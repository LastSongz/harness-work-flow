# 华为海思供应链 SDD 需求到 Spec MR 规范 v0.1

## 文档定位

- 状态：Draft
- 适用范围：从业务方下发 RR 到 Spec MR 合入代码仓库
- 当前约束：一个 US 对应一个代码仓库内的一个 Spec 目录
- 更新日期：2026-07-14

本规范不替换华为现有需求管理流程，而是在开发者接收 US 后补充仓库内 Spec。目标是把需求澄清、系统行为、技术契约和验收标准沉淀为可版本化、可评审、可追溯的开发基线。

## 1. 端到端流程

~~~text
业务方下发 RR
  → PO 评审，形成 IR
  → BA 分析 IR，拆解为 US
  → 开发者接收 US，创建 Draft Spec MR
  → 围绕 Spec 进行需求反串讲
  → BA、开发、测试评审，结论回写 Spec 正文
  → Spec MR 达到 Ready 并获得批准
  → MR 合入主分支，形成 Approved Spec 基线
  → 开发者拆解 Task，给出正式工作量和预计完成时间
~~~

v0.1 采用以下映射：

~~~text
一个 IR → 一个或多个 US
一个 US → 一个 Spec 目录
一个 Spec 目录 → 一组开发 Task
~~~

## 2. 事实源边界

| 产物 | 主要负责人 | 主要作用 | 事实源 |
|---|---|---|---|
| RR | 业务方 | 描述原始业务诉求 | 华为需求系统 |
| IR | PO、BA | 确认进入交付的需求 | 华为需求系统 |
| US | BA | 描述本次交付的用户能力 | 华为需求系统或看板 |
| Spec | 开发者、BA、开发、测试 | 明确系统行为、技术契约和验收标准 | 代码仓库 |
| Task | 开发者 | 实施已批准的 Spec | 华为研发任务系统 |

华为需求系统仍是业务来源、优先级和范围的事实源；代码仓库中的 Approved Spec 是系统行为、技术契约和验收标准的事实源。两者通过 RR、IR、US 编号及链接建立追溯。

聊天、会议纪要和 MR 评论可以用于讨论，但其中形成的有效结论必须回写 Spec 正文。没有回写的内容不作为开发依据。

## 3. Spec 内容与责任

承接 US 的开发者默认担任 Spec Owner，负责创建 Draft MR、补充工程细节并收敛评审意见。BA 确认 Spec 不偏离 IR、US 和业务规则；开发负责人确认技术方案与影响范围；测试负责人确认验收标准和场景可测试。

推荐目录：

~~~text
specs/<US编号>-<简短名称>/
├── requirements.md  # 追溯信息、目标、范围、业务规则和验收标准
├── design.md        # 技术方案、接口、数据、异常、兼容和测试策略
├── tasks.md         # 实施顺序、依赖、完成条件及外部 Task 链接
└── decisions.md     # 反串讲和评审形成的重要决策
~~~

Spec 不复制 RR、IR、US 的全部内容，而是引用上游需求，并补充实现和验收所必需的信息。

## 4. Spec MR 生命周期

### Draft：用于澄清

需求分析形成基本结构后即可创建 Draft MR，不必等待全部问题解决。至少应包含：

- RR、IR、US 的编号或链接；
- 目标、初步范围和非目标；
- 主要流程、核心规则和初步验收标准；
- 已知假设、风险和开放问题。

反串讲围绕 Draft Spec 展开。业务规则写入 `requirements.md`，技术结论写入 `design.md`，重要取舍写入 `decisions.md`。

### Ready：用于批准

同时满足以下条件，Draft MR 才能标记为 Ready：

- Spec 与 RR、IR、US 的追溯完整；
- 目标、范围、业务规则和术语明确；
- 正常、异常、权限和边界场景已覆盖；
- 验收标准可观察、可测试；
- 技术影响、接口、数据和兼容策略明确；
- 阻塞性开放问题为零；
- 有效讨论结论已回写正文；
- `requirements.md`、`design.md` 和 `tasks.md` 相互一致。

### Merge：形成基线

BA 或业务负责人批准业务内容，开发负责人批准技术内容，测试负责人批准验收与测试内容。评审线程关闭、Spec 状态更新为 `Approved` 后，MR 才可合入主分支。

~~~text
Approved Spec 基线 = Spec 目录 + 主分支 + Merge Commit SHA
~~~

Draft MR 用于澄清，Ready MR 用于批准，Merge Commit 用于建立正式开发基线。Spec MR 原则上不混入正式业务代码。

## 5. Task 与估算

工作量评估分为两次：

1. 开发者接收 US 后可给出区间式初步估算，用于排期判断，但不作为最终承诺；
2. Spec Approved 且 Task 拆解完成后给出正式估算，作为交付计划依据。

Task 的负责人、状态和工时以华为研发任务系统为准。仓库内 `tasks.md` 只记录实施逻辑、依赖、完成条件、验证方式和外部 Task 链接，避免重复维护状态。

## 6. 变更原则

- RR、IR、US 的范围或优先级变化，先按华为现有流程处理；
- 影响系统行为、技术契约或验收标准的变化，必须同步提交 Spec 变更 MR；
- 不能通过 Spec 绕过上游审批，也不能只更新需求系统而不更新 Spec；
- 后续开发和 Code MR 必须引用 Approved Spec 基线；
- 实现采用增量修改，不根据 Spec 全量重写存量代码。

## 一句话规范

> RR、IR、US 管理业务来源与交付范围；仓库内 Approved Spec 管理系统行为、技术契约和验收标准。开发者以 Draft MR 组织澄清，以 Ready MR 完成批准，以 Merge Commit 建立基线，再拆 Task 并进行正式估算。
