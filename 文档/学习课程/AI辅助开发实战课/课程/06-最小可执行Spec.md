# 最小可执行 Spec：用户故事、业务规则、边界、非功能需求

导航：上一篇 [[05-AI阅读陌生代码库]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一篇 [[07-Plan Before Code]]

> [!summary] 核心问题
> 用户故事太短会留下歧义，设计文档太细又会过早锁死实现。最小可执行 Spec 要做的，是用可观察行为、边界和非功能要求表达“系统必须做到什么”，同时把“具体怎么做”留给 Plan。


## 最小不等于模糊，可执行不等于写实现

最小可执行 Spec 至少回答：

- 谁在什么条件下要获得什么结果？
- 哪些业务规则必须成立？
- 输入、输出、错误和状态如何被观察？
- 系统边界外发生什么，哪些内容本次不处理？
- 性能、安全、一致性、审计等非功能要求如何验收？

Spec 描述可观察行为和约束，Plan 再决定类、方法、表结构和调用顺序。过早把实现写进 Spec 会限制方案；只写一句用户故事又不足以驱动测试。

## 订单取消最小 Spec

### 用户故事

作为尚未收到商品的用户，我希望取消符合条件的订单，以停止履约并在已支付时发起一次退款。

### 业务规则

1. `CREATED` 可直接转为 `CANCELED`。
2. `PAID` 接受取消后进入 `CANCELING`，系统创建唯一退款任务；退款成功后转为 `CANCELED`。
3. `SHIPPED` 拒绝取消，返回稳定错误码 `ORDER_NOT_CANCELABLE`。
4. 相同订单与 `requestId` 的重复请求返回原结果，不创建第二个退款任务。
5. 两个不同 `requestId` 并发取消同一订单时，最多一个请求推进状态。
6. 每次尝试都记录操作者、原因、请求标识、原状态、结果和时间。

> [!note]
> 前一版任务简报仍假设退款可以同步完成。代码探索确认外部退款不属于本地事务后，这里增加 `CANCELING` 作为一致性边界。这正是 Spec 在编码前吸收事实、消除歧义的作用。

### 接口场景

```gherkin
场景：取消已创建订单
假如订单 O-100 处于 CREATED
当用户以 requestId=R-1 请求取消
那么接口返回成功
并且订单状态为 CANCELED
并且不创建退款任务

场景：重复取消已支付订单
假如订单 O-200 处于 PAID
当用户两次以 requestId=R-2 请求取消
那么两次响应表示同一取消结果
并且仅存在一个退款任务
```

### 非功能要求

- 单次 API 在不等待外部退款完成时于 500ms 内返回。
- 取消与退款任务写入必须处于同一本地事务。
- 日志不记录支付令牌、银行卡或完整个人信息。
- 关键场景可由自动化测试重复验证。

### 不包含

- 前端交互改版、支付 SDK 升级、人工强制取消已发货订单。
- 退款供应商内部重试策略和历史订单批量迁移。

## 可以怎样做

1. 从任务简报提取用户、触发条件和价值。
2. 把每个状态写成“允许/拒绝/结果”规则。
3. 对外部副作用增加幂等、一致性和失败后的可观察状态。
4. 把规则改写成 Given/When/Then 场景。
5. 写 3～5 条能被测试或监控证明的非功能要求。
6. 明确不包含项，防止实现范围扩张。

## 动手梳理

补写三个场景：

- `SHIPPED` 订单取消被拒绝且状态不变。
- 两个不同请求并发取消，只产生一个退款任务。
- 退款暂时失败，订单保持 `CANCELING`，错误被审计且可重试。

每个场景都必须包含初始状态、动作、响应、最终状态和副作用数量。

## 自查清单

- [ ] 用户故事、业务规则、场景、非功能要求和不包含项齐全。
- [ ] 每条状态规则都能转成测试。
- [ ] 外部退款的幂等和失败状态可观察。
- [ ] Spec 没有指定未经比较的类结构或框架细节。
- [ ] Spec 与代码探索事实一致。

## 实战速查卡

### 什么时候查这篇文章

- 需求讨论结束后仍说不清边界。
- 测试人员无法从需求推出用例。
- Spec 写满类名和表结构。
- 外部副作用失败时没有可观察状态。

### 先做什么

- 从任务简报提取用户、触发条件和价值。
- 把状态写成允许、拒绝和结果。
- 为外部副作用补幂等与失败状态。
- 用 Given/When/Then 表达。
- 明确非功能要求和不包含项。

### 可直接借鉴的方法

用户故事 → 业务规则 → 接口场景 → 非功能要求 → 不包含范围。每条规则都应能变成测试，但不要提前指定未经比较的类结构。

### 常见误区

- 只写一句用户故事。
- 把实现方案当成需求。
- 用“高性能、安全”而没有指标。
- 不写明确不包含项。

### 完成证据

- 可测试的业务规则。
- 覆盖成功、拒绝、重复、并发和失败的场景。
- 可验证的非功能要求。
- 与代码探索一致的不包含范围。
