# 08 任务拆分：垂直切片、小 PR、依赖、检查点和回滚点

导航：上一课 [[07-Plan Before Code]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一课 [[09-上下文工程]]

## 本课目标

- 把大 Plan 拆为可独立验证的垂直切片。
- 显式记录任务依赖、文件所有权、检查点和回滚点。
- 避免“先生成所有层，最后统一测试”的大爆炸交付。

## 讲解：按可观察能力切，不按技术层堆半成品

“先写 Controller、再写 Service、再写 Repository”让每一步都无法独立证明业务价值。垂直切片应从一个验收场景穿过必要层，并在结束时有测试证据。

一个合格小任务应具备：

- 单一、清晰的验收结果。
- 可列举的文件范围和所有者。
- 已知输入依赖和对后续任务的输出。
- 目标测试、检查点和失败停止条件。
- 能单独撤销或恢复的边界。

小 PR 不是越小越好。只改一个 DTO 却让仓库无法编译，不是可审阅切片；把状态、退款、审计、迁移和所有测试塞进一个 PR，也不是。

## 示例：四个垂直切片

| 切片 | 可交付行为 | 主要范围 | 验证 |
|---|---|---|---|
| 1 | CREATED 订单经 API 取消为 CANCELED | Domain、UseCase、Controller | 领域测试 + MockMvc |
| 2 | PAID 订单写入 CANCELING 与唯一退款任务 | Domain、Outbox、事务服务 | 应用集成测试 |
| 3 | 退款 Worker 成功/失败可重试且幂等 | Handler、RefundGateway | 调用次数 + 状态测试 |
| 4 | 并发、审计、完整错误契约 | 锁、审计、异常映射 | 并发测试 + 契约测试 |

依赖关系是 `1 → 2 → 3`，切片 4 的审计字段可与 3 并行研究，但修改同一领域对象时仍应串行合并。

## 检查点与回滚点

```text
检查点 A：切片 1 目标测试全绿，Diff 只含取消 CREATED 所需范围。
回滚点 A：可独立撤销切片 1，不影响现有订单查询。

检查点 B：切片 2 的订单状态与 outbox 同事务；重复 requestId 唯一。
停止条件 B：需要新增表但迁移策略未批准。

检查点 C：Fake RefundGateway 证明成功、失败和重复消费。
回滚点 C：禁用 Worker 消费，不删除已记录的取消意图。
```

## 操作步骤

1. 把 Spec 场景按业务价值排序：最简单成功路径→外部副作用→失败/并发。
2. 为每个场景切出最少跨层文件。
3. 标出共享热点文件，避免两个任务同时改同一符号。
4. 为每个任务写“进入条件、完成证据、停止条件”。
5. 规划合并顺序和可恢复操作。
6. 每个切片结束都审查 Diff，再启动下一个。

## 练习

把“实现订单取消全部功能”拆成 3～5 张任务卡。每张必须写：

```markdown
目标行为：
文件所有权：
依赖：
目标测试：
检查点：
停止条件：
回滚方式：
```

然后检查：是否存在没有用户可观察结果的纯技术任务？若存在，把它合并进需要该基础设施的切片。

## 验收标准

- [ ] 每个任务都有独立可验证行为。
- [ ] 依赖和合并顺序明确。
- [ ] 共享文件不会被并行任务同时修改。
- [ ] 每个任务都有检查点、停止条件和回滚方式。
- [ ] 没有产生长期不可运行的中间状态。
