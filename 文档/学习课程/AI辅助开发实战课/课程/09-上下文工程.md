# 09 上下文工程：相关上下文、噪声、新会话与上下文压缩

## 本课目标

- 为当前决策提供足够但不过量的上下文。
- 识别长会话中的噪声和错误锚点。
- 写出可让新会话安全恢复工作的交接摘要。

## 讲解：更多上下文不等于更好

上下文可以分三层：

- **稳定层**：仓库规则、构建命令、架构边界、业务术语。
- **任务层**：已批准 Spec、Plan、目标文件、验收和当前 Diff。
- **临时层**：本轮错误输出、实验结果、尚未证实的假设。

稳定层应通过项目规则长期维护；任务层随任务携带；临时层在做出结论后压缩为事实或删除。把整个仓库、全部聊天和长日志一次性塞给 Agent，会稀释关键约束，还可能保留已经推翻的假设。

## 相关上下文包示例

执行“切片 2：PAID 取消意图”时，只需要：

```text
稳定规则：
- 使用 Java 21 / Spring Boot 3；./mvnw test 为标准命令。
- 领域对象不直接调用外部网关；不自动提交。

任务资产：
- Spec 中 PAID、requestId、一致性与审计规则。
- 已批准 Plan 的切片 2。
- Order、OrderRepository、现有 Outbox 示例及对应测试。

当前状态：
- 切片 1 已通过，提交/检查点为 abc123（练习标识）。
- 目标测试：PaidOrderCancellationTest、CancelOrderUseCaseIT。
- 未修改 RefundRequestedHandler，它属于切片 3。
```

不需要加入前端文档、全部支付 SDK 源码、已修复的编译错误或其他功能聊天。

## 什么时候开新会话

- 切换到不同功能或不同切片。
- Agent 连续重复同一错误，已经被旧假设锚定。
- 当前切片完成，需要独立审查。
- 会话经过多次摘要，关键约束开始丢失。

同一问题的紧密调试可以继续原会话，因为错误、实验和刚修改的 Diff 仍然相关。

## 交接摘要示例

```markdown
目标：完成 PAID 订单取消意图，不实现退款 Worker。
基线：Spec v2；Plan 切片 2；切片 1 已验证。
已完成：Order 支持 PAID→CANCELING；同事务写 RefundRequestedOutbox。
证据：两个目标测试通过；相关模块测试通过。
当前 Diff：Order、CancelOrderUseCase、Outbox 及对应测试，共 6 个文件。
未完成：数据库迁移尚未批准，因此没有新增表。
下一步：评审现有 outbox 表能否复用；若不能，停止并提交迁移决策。
禁止：不要实现 Worker，不提交、不推送，不改支付 SDK。
```

## 操作步骤

1. 每轮开始先问：当前要做出的下一个决策是什么？
2. 只加入能改变该决策的信息。
3. 长日志保留原始文件位置，聊天中提取错误、命令和关键行。
4. 假设被推翻后明确记录新结论，避免旧结论继续影响 Agent。
5. 切片结束生成交接摘要，再开新会话做独立评审或下一任务。

## 练习

从以下内容中选择切片 2 必需上下文：订单 Spec、前端截图、Order 源码、全部 Git 历史、Outbox 相邻实现、目标测试、支付供应商市场宣传页、当前 Diff、数据库密码。

正确选择应包含 Spec、Order、Outbox 模式、目标测试和当前 Diff；数据库密码绝不能进入上下文。

再按示例写一份不超过 10 行的交接摘要。

## 验收标准

- [ ] 上下文按稳定、任务和临时三层组织。
- [ ] 每个加入项都能解释它影响什么决策。
- [ ] 摘要包含目标、基线、证据、Diff、未完成和禁止项。
- [ ] 秘钥、无关长日志和过期假设未进入上下文。
- [ ] 知道何时继续原会话、何时新开会话。

## 课后小结

上下文工程不是堆材料，而是维持当前决策的信噪比。下一课把真正稳定、会反复使用的知识沉淀为项目长期记忆。
