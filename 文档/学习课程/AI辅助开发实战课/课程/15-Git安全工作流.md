# Git 安全工作流：窄变更、分支、Worktree、原子提交、可恢复操作

导航：上一篇 [[14-AI代码评审]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一篇 [[16-多Agent并行]]

> [!summary] 核心问题
> Git 不只是交付代码的最后一步，也是 Agent 工作流的恢复层和审计层。窄变更、原子提交、明确分支和可恢复操作，让自动化犯错时仍能快速看见、隔离和撤销。


## Git 是 Harness 的恢复与审计层

Agent 开始修改前先回答：

- 当前 Git 根目录是不是目标仓库？
- 当前分支和远端关系是什么？
- 哪些未提交文件属于用户？
- 本任务预期修改哪些文件？
- 什么动作需要批准：建分支、提交、推送、开 PR、改历史？

默认保留所有未知改动。不要用覆盖工作树的命令清理“碍事”文件，也不要在混合工作树中笼统暂存全部内容。

## 安全流程示例

```bash
git rev-parse --show-toplevel
git status --short --branch
git diff --name-only
```

记录基线后，在 `codex/order-cancellation` 等独立分支工作。需要并行任务时使用 Worktree，让每个任务拥有独立目录和索引，而不是多个 Agent 同时操作同一工作树。

完成一个切片后：

```bash
git diff -- src/main/java/.../Order.java src/test/java/.../OrderTest.java
git diff --check
git add src/main/java/.../Order.java src/test/java/.../OrderTest.java
git diff --cached --name-only
git diff --cached --check
```

只有在用户已授权提交时，才创建描述单一意图的提交。提交信息说明“为什么”，PR 再补 Spec、验证命令、风险和回滚方式。

## 原子提交与恢复

订单取消可以按可运行切片形成提交：

1. `feat: 支持已创建订单取消`
2. `feat: 记录已支付订单退款意图`
3. `feat: 幂等处理退款任务`
4. `test: 覆盖并发取消与审计`

每个提交都应能构建并说明自己的验证。恢复优先使用可审计操作：停止合并、撤销单个提交、关闭功能开关、回退部署版本。改写共享历史、强制推送、批量删除或覆盖用户工作树属于高风险动作，必须单独授权。

## Worktree 使用边界

Worktree 适合：

- 两个独立切片需要并行且文件不重叠。
- 主工作树已有用户改动，需要隔离新任务。
- 独立评审者要在干净基线上复现测试。

不适合：

- 两个任务都修改 `Order.java` 和同一迁移文件。
- 任务太小，隔离成本高于收益。
- 团队没有定义分支、合并和清理责任。

## 可以怎样做

1. 检查 Git 根、分支、dirty state 和远端状态。
2. 写预期文件清单，标记用户已有改动。
3. 选择当前分支、专用分支或 Worktree。
4. 每个切片后检查未暂存与已暂存 Diff。
5. 只精确暂存任务文件，运行 staged 检查。
6. 获得授权后再提交、推送或创建 PR。
7. 在 PR 中记录验证、风险和恢复方式。

## 动手梳理

当前状态：

```text
M src/main/java/.../Order.java        （用户正在修改）
M README.md                           （用户笔记）
?? src/test/java/.../CancelOrderTest.java （Agent 新增）
```

写出安全处理方案。正确方向是先识别 `Order.java` 的用户改动是否与任务重叠；不能覆盖或整文件暂存它。必要时新建 Worktree 或让用户先决定所有权；`README.md` 不属于任务；测试文件也只有在对应实现范围明确后才精确暂存。

## 自查清单

- [ ] 修改前已记录 Git 根、分支和 dirty state。
- [ ] 用户已有改动得到保留并与任务 Diff 区分。
- [ ] 暂存使用精确路径，并检查 staged 文件与空白错误。
- [ ] 每个提交单一意图、可构建、可撤销。
- [ ] 高风险 Git 动作需要单独授权。

## 实战速查卡

### 什么时候查这篇文章

- 工作区已有他人未提交改动。
- Agent 想直接 git add -A。
- 一个提交混入多个意图。
- 并行任务互相覆盖。
- 不知道怎样安全撤销。

### 先做什么

- 先确认仓库边界与 dirty state。
- 只修改和暂存授权文件。
- 每个切片形成原子提交。
- 危险操作前解析准确目标。
- 推送前复核提交与远端差异。

### 可直接借鉴的方法

基线检查 → 窄修改 → 目标验证 → 精确暂存 → cached Diff 审查 → 原子提交 → 推送/PR。并行任务优先使用独立分支或 Worktree。

### 常见误区

- 默认 git add -A。
- 用 reset --hard 清理未知改动。
- 提交生成物和无关格式化。
- 把 Worktree 当成自动解决冲突。
- 推送前不看 ahead/behind。

### 完成证据

- 明确仓库根目录。
- 精确暂存文件清单。
- cached diff --check。
- 可独立撤销的提交。
- 推送后本地与远端 SHA 一致。
