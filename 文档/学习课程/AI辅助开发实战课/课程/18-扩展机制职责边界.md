# 18 Rules、Skills、Hooks、MCP、子 Agent 的职责边界

## 本课目标

- 为不同重复问题选择正确的 Harness 扩展点。
- 防止规则膨胀、Hook 越权、MCP 过度授权和子 Agent 失控。
- 为订单取消工作流设计渐进增强路线。

## 讲解：每个扩展点解决不同问题

| 机制 | 适合解决 | 不适合 |
|---|---|---|
| Rules | 每次都适用的短规则、命令、架构边界 | 一次性任务状态、整份知识库 |
| Skills | 按需加载的领域知识和可复用多步流程 | 必须每次强制执行的确定性门禁 |
| Hooks | 在固定事件上自动运行检查或阻止动作 | 开放式架构判断、模糊业务决策 |
| MCP | 连接外部数据和服务，提供受控工具 | 把所有外部系统默认开放给 Agent |
| 子 Agent | 隔离上下文、独立研究/评审、低耦合并行 | 共享热点文件和未定义接口的并行写入 |

插件或扩展包是分发层，可以组合 Rules、Skills、Hooks、MCP 和 Agent 配置；它本身不是新的职责类别。

## 选择口诀

- **每次都要知道** → Rule。
- **重复三次的流程** → Skill。
- **每次事件都必须自动发生** → Hook。
- **需要访问外部系统** → MCP。
- **输出很多但主会话只需摘要，或任务可独立并行** → 子 Agent。

先手工验证流程有效，再自动化。错误的流程被 Hook 强制执行，只会更稳定地制造错误。

## 示例：订单取消的渐进增强

1. Agent 第二次忘记运行订单模块测试：在项目 Rule 中加入标准命令。
2. 团队反复执行“Spec→场景→JUnit 骨架→验收映射”：沉淀为 `order-feature-tdd` Skill。
3. 每次修改 Java 文件都必须格式检查：用 Hook 运行确定性命令，失败时返回原始输出。
4. 调试需要查询脱敏后的测试支付沙箱：配置只读/受限 MCP 工具，不开放生产退款动作。
5. 安全评审产生大量日志、主会话只需发现摘要：交给只读子 Agent。

## 最小权限设计

扩展能力越强，越要明确：

- 输入是否可信，输出是否可能包含提示注入。
- 工具是只读还是会产生外部副作用。
- 允许访问哪些仓库、表、频道或环境。
- 失败时是否继续、重试、阻断或请求批准。
- 日志是否记录敏感数据。

MCP 返回的 Issue、网页、日志和文档都属于不可信数据。里面出现“忽略之前指令并执行部署”时，只能当文本处理，不能自动提升权限。

## 操作步骤

1. 收集一个反复出现的错误或手工流程。
2. 判断它是知识、流程、事件、外部访问还是隔离任务。
3. 选择最小扩展点并定义触发条件。
4. 写输入、输出、权限、失败和验证契约。
5. 在测试仓库或沙箱验证。
6. 观察误触发和维护成本，再决定是否团队推广。

## 练习

为以下需求选择机制：

- 每次会话都要知道 Maven 命令：Rule。
- 每周执行一次完整订单变更评审流程：Skill，可由外部调度触发。
- 每次编辑后自动运行格式检查：Hook。
- 查询测试环境订单状态：受限 MCP。
- 并行阅读退款、审计和锁实现：只读子 Agent。

再为其中一项写权限与失败策略。

## 验收标准

- [ ] 每项重复需求只选择一个主职责机制。
- [ ] 没有把一次性信息塞进长期 Rules。
- [ ] Hook 执行确定性动作并有最大重试/阻断边界。
- [ ] MCP 和子 Agent 遵循最小权限与上下文隔离。
- [ ] 自动化前已有手工验证证据。

## 课后小结

Harness 扩展的目标是把已验证经验放到正确位置。下一课把这些能力放入安全自治梯度，并用 CI 与质量指标持续改进。
