# 结业实战：Spec→Plan→Tests→Code→Review→Commit/PR

导航：上一篇 [[19-安全自治与持续改进]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]]

> [!summary] 核心问题
> 真正的 Agentic Engineering 能力，不是记住术语，而是把一次需求稳定地走完：确认基线、固化 Spec、比较 Plan、用测试驱动实现、根据工具反馈修正、独立评审，并形成可恢复的 Git 交付。


## 结业实战验证流程，而不是比拼生成速度

这里复用前面文章已经形成的任务简报、代码地图、Spec、Plan 和项目规则，只实现一个可独立验证的垂直切片。重点是控制范围并判断何时停止：如果仓库基线、业务规则或环境不满足前提，应留下证据并暂停，而不是为了宣布“完成”而跳过验证。

最终评分看资产是否一致、反馈是否真实、Diff 是否可审查，以及高风险动作是否得到批准；代码行数和提示词长度都不是结业指标。

## 实战任务

在练习 Spring Boot 仓库实现：

```text
CREATED 订单收到合法的取消请求后变为 CANCELED；
返回稳定成功响应；
记录 requestId、原因、操作者、原状态和时间；
不创建退款任务；
SHIPPED 订单仍被拒绝。
```

禁止顺手实现 PAID 退款、数据库新表、前端页面、提交或推送。若仓库与假设不一致，优先适配现有模式；需要改变公开契约或迁移时停止演练并记录决策。

## 第一步：基线与 Harness（3 分钟）

```markdown
Git：确认根目录、分支、dirty state，保护用户改动。
规则：读取项目指令、构建命令和相邻取消/状态变更示例。
权限：允许读、限定文件编辑和目标测试；不允许外部系统、提交、推送。
反馈：目标测试→相关测试→静态检查→Diff→独立评审。
```

## 第二步：复核 Spec 与 Plan（5 分钟）

**Spec 场景**

```gherkin
假如订单处于 CREATED
当拥有者以唯一 requestId 和非空原因请求取消
那么订单变为 CANCELED
并记录完整审计
并且退款任务数量为 0
```

**文件级 Plan**

1. 读取 `Order` 和最接近的状态测试，确认领域模式。
2. 先新增 `OrderCancellationTest` 的 CREATED 成功与 SHIPPED 拒绝场景。
3. 最小修改领域方法；若现有应用服务已提供入口则复用。
4. 补应用/HTTP 层的稳定响应测试。
5. 运行目标测试、相邻测试和 Diff 检查。

## 第三步：Red-Green 实现（8 分钟）

1. 写 CREATED 成功测试并运行，保存预期失败。
2. 写最小领域实现，使状态与审计断言通过。
3. 写 SHIPPED 拒绝测试，确认现有或新增规则通过。
4. 如需应用/HTTP 层，只补当前场景所需最小契约。
5. 每轮只围绕一个失败修改，不批量生成所有层。

执行日志至少记录：

```markdown
假设：Order 缺少 CREATED→CANCELED 领域转换。
修改：Order.requestCancel 与对应领域测试。
命令：./mvnw -Dtest=OrderCancellationTest test
结果：测试数、通过/失败、关键错误。
下一步：扩大到 OrderTest 和应用服务测试。
```

## 第四步：扩大验证与调试（5 分钟）

- 运行相邻订单测试和模块标准检查。
- 查看是否真的发现并执行了目标测试。
- 若失败，按 [[13-证据驱动调试]] 的方法记录复现、假设和最小实验。
- 查看 Diff：只应出现当前切片文件，没有无关格式化。
- 检查日志、错误码、审计和鉴权是否符合项目模式。

## 第五步：独立评审与修正（5 分钟）

让独立审阅者只读检查：

```text
对照当前小切片 Spec 和 Diff 查找行为、架构、异常、安全、性能或兼容问题。
每条发现附文件位置、触发场景、影响、证据和最小修复。
不要修改文件，不要只总结代码。
```

只修复证据充分且属于当前范围的问题；新增需求回到 Spec，不在评审阶段偷偷扩张。

## 第六步：Git/PR 交接（4 分钟）

在获得授权前只准备，不执行提交或推送：

```markdown
变更目的：支持 CREATED 订单安全取消。
Spec 场景：成功取消、SHIPPED 拒绝、审计完整、无退款任务。
修改范围：列出实际文件。
验证证据：列出实际命令与结果。
评审修正：列出发现和处理。
剩余风险：PAID/退款、并发和迁移不在本切片。
恢复方式：撤销本切片提交或关闭对应功能开关。
```

若用户明确授权，再精确暂存、检查 staged Diff、创建原子提交并开 PR；否则把上述内容作为交接材料。

## 动手完成闭环

完成实战后，用 2 分钟回答：

1. 哪个事实是在代码探索后改变了原计划？
2. 哪条测试最早阻止了错误实现？
3. 哪个动作需要人工批准，为什么？
4. 哪个重复问题值得沉淀为 Rule、Skill 或 Hook？
5. 如果扩展到 PAID 退款，下一张独立任务卡是什么？

## 自查清单

- [ ] Git 基线、项目规则、权限和停止条件已确认。
- [ ] Spec、Plan、测试和实际 Diff 能一一对应。
- [ ] 至少完成一次真实 Red-Green 循环并保存命令结果。
- [ ] 相关测试、静态检查和 Diff 检查有证据。
- [ ] 独立评审有结论，问题修正或明确记录。
- [ ] 交接材料包含范围、验证、风险和恢复方式。
- [ ] 未经授权没有提交、推送、迁移或访问外部生产系统。

## 实战速查卡

### 什么时候查这篇文章

- 想确认自己的 AI 开发流程是否完整。
- 知道很多方法却不会串联。
- 准备把订单取消功能交付为真实变更。
- 需要整理一份可审查的证据包。

### 先做什么

- 确认仓库基线和 Harness。
- 复核 Spec 与 Plan。
- 按垂直切片执行 Red-Green。
- 扩大验证并调试。
- 独立评审。
- 精确暂存、提交并准备 PR。

### 可直接借鉴的方法

最终交付包应包含：任务简报、Spec、Plan、任务切片、测试证据、执行日志、评审记录、Diff、提交说明、剩余风险和回滚路径。

### 常见误区

- 为了完成流程而一次生成所有资产。
- 测试和实现同时写完。
- 实现者自评后直接交付。
- 混入无关 Diff。
- 提交说明没有验证证据。

### 完成证据

- 从意图到提交的可追踪资产链。
- 关键测试。
- 独立评审。
- 窄 Diff。
- 原子提交。
- 明确的未验证风险与人工签字点。

## 结语

完整闭环的核心不是生成速度，而是每一步都有意图、边界、证据和恢复路径。做到这一点，Agent 才真正成为可依赖的工程执行者。
