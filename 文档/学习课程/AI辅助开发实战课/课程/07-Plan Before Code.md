# 07 Plan Before Code：方案比较与文件级实施计划

导航：上一课 [[06-最小可执行Spec]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一课 [[08-任务拆分]]

## 本课目标

- 在写代码前比较至少两个可行方案。
- 用约束和风险做选择，而不是接受 Agent 的第一个答案。
- 产出能被逐项执行和审查的文件级 Plan。

本课继续围绕订单取消功能，在同步退款与异步退款之间做方案比较，并把选择展开到具体文件与测试。

## 30 分钟安排

| 环节 | 时间 |
|---|---:|
| Plan 的职责 | 5 分钟 |
| 方案比较 | 8 分钟 |
| 文件级示例 | 9 分钟 |
| 练习与验收 | 6 分钟 |
| 小结 | 2 分钟 |

## 讲解：Spec 定义“什么”，Plan 解释“怎么安全改变”

好的 Plan 必须建立在代码地图和 Spec 上，并包含：

- 方案比较、选择理由和放弃理由。
- 按执行顺序列出的具体文件和符号。
- 数据流、事务、错误、兼容和迁移影响。
- 每一步的测试、检查点和停止条件。
- 预期 Diff 范围与回滚方式。

Plan 不是“修改 Service、补充测试”这样的标题清单。审阅者应该能在未改代码前发现遗漏，例如 DTO 没有 `requestId`、退款任务缺少唯一键、异常没有映射。

## 示例：两种退款方案

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A 同步退款 | API 内调用退款，成功后保存 CANCELED | 流程直观 | 外部成功而本地提交失败时难以恢复；响应受外部延迟影响 |
| B 本地意图 + 异步退款 | 同一事务写 CANCELING 与 outbox，Worker 幂等退款后写 CANCELED | 本地一致、可重试、响应快 | 增加状态、Worker 和事件运维成本 |

根据第 06 课的一致性与 500ms 要求，选择方案 B。若真实仓库已有可靠 Saga/工作流框架，应优先复用现有模式，而不是新造 outbox。

## 文件级 Plan 示例

```markdown
1. 修改 domain/Order.java
   - 新增 requestCancel(requestId, reason, operator)；
   - 实现 CREATED→CANCELED、PAID→CANCELING、拒绝状态与乐观锁语义。
   - 先补 OrderTest 的状态表和重复请求测试。

2. 新增 application/CancelOrderUseCase.java
   - 读取订单、鉴权、调用领域方法；
   - 在同一事务保存订单、审计和 RefundRequestedOutbox。
   - 用应用服务测试证明一个 requestId 只写一个 outbox。

3. 修改 web/OrderController.java 与 ApiExceptionHandler.java
   - 接收 reason/requestId，映射 200/202/409 和稳定错误码。
   - 补 MockMvc 契约测试。

4. 新增 integration/RefundRequestedHandler.java
   - 使用 requestId 作为供应商幂等键；
   - 成功推进 CANCELED，失败保留 CANCELING 并记录可重试结果。
   - 用假的 RefundGateway 验证调用次数与失败分支。

5. 验证
   - 目标单元测试→模块测试→静态检查→完整 Diff 审查。
   - 如需新表或改变公开 API，先停止并走迁移/兼容评审。
```

## 操作步骤

1. 把 Spec 中每条规则映射到候选责任位置。
2. 提出 2～3 个真实可行方案，比较一致性、复杂度、兼容和运维。
3. 选择方案并记录放弃理由。
4. 按依赖顺序列出文件、符号、行为和对应测试。
5. 加入数据库、外部接口、异常、安全和性能检查。
6. 请另一名审阅者或独立 Agent 只评审 Plan，不让它直接改代码。

## 练习

检查示例 Plan 是否覆盖以下规则：`SHIPPED` 拒绝、重复 `requestId`、并发取消、审计字段、退款失败。为每条写出对应步骤和测试；找不到映射的规则就是 Plan 缺口。

再写一条明确停止条件：如果现有订单表没有版本字段且项目无锁模式，必须先评审并发方案，不能直接添加迁移。

## 验收标准

- [ ] 至少比较两个方案并记录选择依据。
- [ ] 每条 Spec 规则都能映射到文件和测试。
- [ ] Plan 说明事务、外部失败和并发影响。
- [ ] 每一步都有验证方式，不存在一次性大改。
- [ ] 高风险变化有停止条件。

## 课后小结

Plan 是编码前最便宜的缺陷发现点。下一课把文件级 Plan 切成可独立审阅、可并行但不互相踩踏的小任务。
