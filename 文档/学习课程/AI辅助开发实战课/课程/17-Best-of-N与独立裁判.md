# 17 Best-of-N 与独立裁判：多方案、交叉评审、避免同源错误

导航：上一课 [[16-多Agent并行]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一课 [[18-扩展机制职责边界]]

## 本课目标

- 知道何时值得为同一问题生成多个方案。
- 先定义评分标准，再让独立裁判比较证据。
- 降低同一模型、同一上下文造成的同源错误。

| 环节 | 时间 |

| 适用边界 | 5 分钟 |

## 讲解：多生成不等于多样性

Best-of-N 适合：

- 架构方案有真实权衡，错误成本高。
- 复杂 Bug 有多个合理根因，需要竞争假设。
- 评审高风险 Diff，希望减少单一审阅盲区。

不适合明确机械修改、已有唯一项目模式或验证成本远高于收益的任务。

如果 N 个方案都看到同一份带偏见的摘要、使用同一提示并互相参考，它们可能重复同一个错误。提高独立性的方法：

- 让方案生成者分别从一致性、最小变更、运维复杂度等角度出发。
- 在生成完成前不互相暴露答案。
- 裁判只看匿名方案、Spec、约束和可验证证据。
- 用真实测试、基准和项目规则否决不成立方案。

## 示例：订单取消三方案

| 方案 | 核心做法 |
|---|---|
| A | API 内同步退款，成功后取消 |
| B | 本地 `CANCELING` + outbox + 异步退款 |
| C | 复用现有订单工作流引擎编排退款与取消 |

先定义评分权重：

| 标准 | 权重 |
|---|---:|
| 满足 Spec 与一致性 | 35 |
| 与现有架构一致 | 25 |
| 故障恢复与可观测 | 20 |
| 实施/迁移成本 | 10 |
| 性能与运维复杂度 | 10 |

裁判必须给出“分数 + 证据 + 未知项”。如果仓库已经有成熟工作流引擎，C 可能优于 B；如果没有，C 的引入成本会显著扣分。不能脱离代码地图只按通用最佳实践判胜。

## 交叉评审流程

1. 方案 A、B、C 分别列假设、改动、失败模式和测试策略。
2. 方案生成完成后互相做反例攻击。
3. 独立裁判对照固定标准评分。
4. 用最便宜的实验验证关键未知，例如现有 outbox 是否支持业务唯一键。
5. 人类决策者选择或组合，但组合后必须重新检查一致性，不能拼出第四个未经评审的方案。

## 操作步骤

1. 判断问题是否值得 N 倍成本。
2. 在生成方案前冻结 Spec、约束和评分表。
3. 隔离生成上下文，要求不同视角。
4. 收集匿名方案和证据。
5. 独立裁判评分并标记信心。
6. 对决定胜负的未知项做实验。
7. 记录选择理由和放弃理由。

## 练习

让三个候选方案分别优先考虑：

- 最小代码改动。
- 最强一致性与恢复能力。
- 最大化复用现有平台能力。

用上面的评分表评审。若没有真实仓库信息，必须把“现有平台是否支持 outbox/工作流”列为未知，不能假装给出最终赢家。

## 验收标准

- [ ] Best-of-N 用在高价值、真实不确定的问题上。
- [ ] 评分标准先于候选答案建立。
- [ ] 方案生成和裁判保持足够独立。
- [ ] 关键结论由代码、测试或实验支持。
- [ ] 选择与放弃理由被记录。

## 课后小结

Best-of-N 用成本换取方案多样性，独立裁判用标准和证据约束选择。下一课把反复有效的方法放进合适的扩展机制，而不是把所有内容都塞进 Rules。
