# 16 多 Agent 并行：所有权、隔离、Worktree、汇总与冲突处理

导航：上一课 [[15-Git安全工作流]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一课 [[17-Best-of-N与独立裁判]]

## 本课目标

- 判断任务是否真的适合并行。
- 为每个 Agent 定义输入、文件所有权、输出和停止条件。
- 用 Worktree/分支隔离执行，并由主 Agent 统一汇总验证。

## 30 分钟安排

| 环节 | 时间 |
|---|---:|
| 并行条件 | 5 分钟 |
| 所有权设计 | 8 分钟 |
| 汇总与冲突 | 9 分钟 |
| 练习与验收 | 6 分钟 |
| 小结 | 2 分钟 |

## 讲解：并行的前提是低耦合，不是 Agent 数量

两个任务适合并行，通常同时满足：

- 不依赖对方尚未确定的接口或决策。
- 不修改同一热点文件、迁移或配置。
- 可以在独立分支/Worktree 中运行自己的验证。
- 输出格式清楚，主任务可以低成本汇总。

探索类工作最容易并行，例如一个 Agent 阅读退款链路，另一个检查现有 outbox 模式，第三个只做 Spec 风险评审。实现类工作必须更谨慎，因为共享领域对象和数据库契约会制造合并冲突与语义冲突。

## 示例：订单取消的并行计划

| Agent | 责任 | 只读/写入范围 | 输出 | 停止条件 |
|---|---|---|---|---|
| A | 调研现有退款与幂等模式 | 只读 payment、integration | 符号路径、模式、风险摘要 | 需要访问真实凭证 |
| B | 调研 outbox 与迁移规范 | 只读 infrastructure、migration | 可复用实现、迁移约束 | 仓库无统一迁移策略 |
| C | 评审订单取消 Spec | 只读 Spec 和状态规则 | 缺失场景与冲突 | 发现业务规则不确定 |
| 主 Agent | 汇总、决策、生成 Plan | 不写代码直到汇总完成 | 单一文件级 Plan | 调研结论互相冲突 |

进入实现后可以这样隔离：

- Worktree 1：切片 1，拥有 `Order`、`CancelOrderUseCase` 与对应测试。
- Worktree 2：退款 Handler 的测试夹具和 `RefundGateway` 适配，不改 `Order`。
- 主 Worktree：只做汇总、接口契约确认和最终验证。

每个 Agent 都要知道自己不是仓库中唯一执行者，不得撤销、重写或“清理”其他人的变化。

## 汇总流程

1. 主 Agent 先收集所有输出，不立即拼接代码。
2. 对齐术语、接口、版本和文件所有权。
3. 冲突时回到 Spec/Plan，由一个决策者选择，不让两个 Agent 继续各自扩展。
4. 按依赖顺序合并，每次只合并一个切片。
5. 每次合并后运行目标测试和跨切片测试。
6. 最后独立审查组合后的整体行为；各分支单独通过不代表集成正确。

## 冲突处理示例

Agent A 假定 `RefundGateway.refund(paymentId)`，Agent B 的现有模式使用 `requestRefund(orderId, requestId, amount)`。不要在合并时临时加重载掩盖冲突。主 Agent 应读取权威接口和 Spec，确定稳定契约，再要求其中一个切片适配。

## 操作步骤

1. 从任务依赖图找真正独立的节点。
2. 为每个 Agent 写唯一责任和禁止修改范围。
3. 选择只读并行、Worktree 并行或串行实现。
4. 规定结构化输出：结论、证据、风险、未决项、验证。
5. 主 Agent 汇总后再授权写入。
6. 按顺序合并并运行集成验证。

## 练习

判断以下任务能否并行：

- 读取退款接口与读取 outbox 规范：可以，只读且独立。
- 两个 Agent 同时修改 `Order.requestCancel`：不可以，共享热点。
- 一个写 Controller，一个决定错误码：暂不可以，接口契约未稳定。
- 一个实现 Worker，一个只做安全评审：可以，但评审者保持只读。

为可并行任务各写一行所有权、输出和停止条件。

## 验收标准

- [ ] 并行任务之间无未解决的接口或文件冲突。
- [ ] 每个 Agent 有明确所有权、禁止范围和结构化输出。
- [ ] 写入任务使用独立分支或 Worktree。
- [ ] 主 Agent 逐项汇总并运行组合验证。
- [ ] 冲突通过 Spec/Plan 决策解决，不靠临时兼容掩盖。

## 课后小结

多 Agent 的价值来自隔离后的吞吐，而不是同时修改更多文件。下一课学习另一种“多”：对同一难题生成多个独立方案，再由独立标准裁判。
