# 13 证据驱动调试：复现、假设、插桩、最小修复、回归测试

导航：上一课 [[12-核心执行循环]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一课 [[14-AI代码评审]]

## 本课目标

- 让 Agent 用可复现证据排除假设，而不是随机改代码。
- 区分症状、根因和修复边界。
- 为并发重复退款问题建立回归测试。

本课聚焦订单取消在并发请求下触发重复退款的故障，用证据链定位真实根因。

| 环节 | 时间 |

## 讲解：先稳定复现，再讨论修复

证据驱动调试采用漏斗：

1. **复现**：记录版本、输入、命令、频率、预期和实际。
2. **定位**：沿数据流找第一次偏离预期的位置。
3. **假设**：提出少量互斥、可证伪的根因。
4. **实验/插桩**：一次只改变一个变量，收集日志、调用次数、线程或数据库证据。
5. **最小修复**：修根因，不压制错误消息或扩大重构。
6. **回归**：新增先红后绿测试，并运行相邻场景。

不要一看到 `NullPointerException` 就到处加空判断；不要因为重试后通过就把问题归因于网络。Agent 适合生成候选假设和查相似路径，人要确保实验能区分这些假设。

## 示例：并发取消导致两次退款

**复现**

```text
给同一 PAID 订单并发发送 requestId=R-10 与 R-11。
20 次运行中有 6 次 RefundGateway 调用两次。
两个请求都在日志中读取到状态 PAID。
```

**候选假设**

| 假设 | 可区分证据 |
|---|---|
| H1 领域规则允许重复取消 | 单线程连续调用也会产生两个决策 |
| H2 乐观锁未生效 | 两个事务都成功提交相同旧版本 |
| H3 outbox 缺少业务唯一键 | 订单只更新一次，但表中有两条退款任务 |
| H4 消费者重复投递 | outbox 只有一条，Handler 调用两次 |

先查询事务提交、订单版本和 outbox 数量。若证据显示一次订单更新、两条 outbox，根因更接近 H3，而不是去修改退款客户端重试。

**最小修复**

- 用 `(order_id, cancellation_request_group)` 或项目认可的业务键建立唯一性。
- 应用层把唯一冲突映射为读取原取消结果。
- `RefundGateway` 继续使用稳定幂等键，形成第二道保护。

**回归测试**

```java
@Test
void concurrent_cancel_requests_create_one_refund_job() throws Exception {
    runConcurrently(
        () -> cancel("O-200", "R-10"),
        () -> cancel("O-200", "R-11"));

    assertThat(refundOutbox.countForOrder("O-200")).isEqualTo(1);
}
```

测试应在修复前稳定暴露问题；若竞争窗口太小，可用屏障控制两个线程同时读取旧状态，而不是靠 `sleep` 猜时序。

## 操作步骤

1. 保存可复制的复现命令和失败频率。
2. 对比成功与失败运行，找第一个差异。
3. 写 2～4 个互斥假设和各自证据。
4. 选择信息增益最高、侵入最小的实验。
5. 只在定位后修改根因。
6. 写回归测试并确认修复前红、修复后绿。
7. 检查相似调用路径是否存在同类问题。

## 练习

假设 outbox 只有一条，但退款供应商收到两次调用。写三条新假设，并为每条指定证据。至少覆盖消息重复投递、Handler 幂等记录和供应商响应超时后的客户端重试。

再写停止条件：如果只能访问含真实支付信息的生产日志，应先获得授权和脱敏方案，不能直接复制给 Agent。

## 验收标准

- [ ] 复现包含版本、输入、命令、预期、实际和频率。
- [ ] 假设可证伪，实验能区分至少两个假设。
- [ ] 修复针对根因，没有顺手大重构。
- [ ] 回归测试在修复前能失败、修复后能通过。
- [ ] 已检查同类路径与数据安全边界。
