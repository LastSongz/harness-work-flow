# AI 代码评审：Diff、架构、异常、安全、性能、数据库迁移

导航：上一篇 [[13-证据驱动调试]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一篇 [[15-Git安全工作流]]

> [!summary] 核心问题
> 测试通过只说明被测试的行为没有失败，不能证明架构、异常、安全、性能和迁移都合理。AI 代码评审的目标不是复述 Diff，而是以独立视角寻找实现者没有覆盖的风险。


## 评审的目标是发现问题，不是赞美实现

AI 评审需要四类输入：

- 已批准的 Spec 与 Plan。
- 基线到当前分支的完整 Diff。
- 相关项目规则和相邻实现。
- 测试/CI 结果及未验证项。

评审顺序：

1. **行为一致性**：每条验收是否实现，是否出现 Spec 外行为。
2. **架构边界**：依赖方向、职责、事务和外部副作用是否合理。
3. **异常与恢复**：失败会留下什么状态，重试是否安全。
4. **安全与隐私**：鉴权、越权、输入、日志、密钥和提示注入。
5. **性能与并发**：N+1、锁范围、热点唯一键、同步外部调用。
6. **数据库与兼容**：迁移顺序、回填、索引、回滚、旧版本兼容。

“测试通过”不能替代这些检查；“看起来不错”也不是评审结论。

## 评审请求

```text
请作为独立审阅者检查当前订单取消 Diff，不修改文件。
基线是 main，依据 Spec v2 和已批准 Plan。

优先寻找会导致错误行为、数据不一致、安全问题、性能退化或迁移失败的缺陷。
每条发现必须包含：
- 严重级别；
- 文件与最小行范围；
- 触发场景；
- 为什么违反 Spec/规则；
- 最小修复方向；
- 建议补充的验证。

如果没有可证实问题，明确写“未发现”，并列出仍未验证的风险。
不要只总结 Diff，不评论纯个人风格偏好。
```

## 订单取消评审示例

假设 Diff 在 `CancelOrderUseCase` 中先保存 `CANCELING`，事务提交后才写 outbox：

```text
[高] 取消状态与退款任务不在同一本地事务
位置：CancelOrderUseCase.java 的状态保存与 outbox 写入之间
触发：订单提交成功后进程崩溃
影响：订单永久停在 CANCELING，且没有可消费退款任务
依据：Spec 要求两者同一本地事务
修复：让同一事务保存订单与 outbox，并补进程中断等价的集成测试
```

其他常见发现：

- Controller 只校验订单存在，没有校验当前用户是否拥有订单。
- `reason` 原样写日志，可能包含个人信息或换行伪造日志。
- 新唯一索引直接加到历史表，未先检查重复数据。
- 退款 Worker 无批次上限，失败任务导致热循环。

## 可以怎样做

1. 确认评审基线和 Diff 范围。
2. 先对照 Spec 做覆盖表，再读实现细节。
3. 分六层检查，不让低价值风格评论淹没行为问题。
4. 对每个发现验证触发路径，避免仅凭可能性报错。
5. 让第二个独立审阅者关注第一轮未覆盖的层。
6. 修复后重跑相关测试，并只复审新增 Diff。

## 动手梳理

评审以下伪代码：

```java
order.setStatus(CANCELED);
orderRepository.save(order);
refundGateway.refund(order.getPaymentId());
log.info("canceled {}, reason={}", orderId, request.reason());
```

至少写四条发现，覆盖事务一致性、状态规则、幂等/并发、日志隐私或鉴权。每条都写触发条件和验证方式。

## 自查清单

- [ ] 评审依据包含 Spec、Plan、规则、Diff 和测试证据。
- [ ] 六层检查均有明确结论。
- [ ] 发现附带位置、触发、影响和最小修复方向。
- [ ] 没有把风格偏好冒充阻塞缺陷。
- [ ] 修复后完成针对性复审。

## 实战速查卡

### 什么时候查这篇文章

- 评审意见只有总结和赞美。
- 测试全绿却不敢合并。
- Diff 涉及数据库或外部接口。
- 实现者同时充当唯一裁判。

### 先做什么

- 先核对 Spec 与范围。
- 按文件阅读真实 Diff。
- 检查行为、架构、异常、安全、性能和迁移。
- 要求问题附路径、证据和影响。
- 修正后重新验证。

### 可直接借鉴的方法

先问“改了什么、为什么、证据是什么”，再分层审查：需求覆盖 → 数据流与事务 → 失败路径 → 安全与性能 → 兼容和迁移 → 测试盲区。

### 常见误区

- 只让 Agent 总结代码。
- 脱离 Spec 挑风格。
- 把所有建议当阻塞项。
- 忽略新增依赖和迁移。
- 让同一上下文中的实现者自审。

### 完成证据

- 带优先级的具体发现。
- 路径与行级证据。
- 剩余风险。
- 修正后的测试与 Diff。
- 独立审查记录。
