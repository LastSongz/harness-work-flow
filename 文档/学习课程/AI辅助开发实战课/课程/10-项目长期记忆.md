# 项目长期记忆：AGENTS.md、CLAUDE.md、Cursor Rules 与路径级规则

导航：上一篇 [[09-上下文工程]] · [[VibeCoding课程首页]] · [[VibeCoding课程总纲]] · 下一篇 [[11-AI与TDD]]

> [!summary] 核心问题
> 如果同一条命令、架构边界或安全要求每次都要重新提醒 Agent，说明它不再只是任务上下文，而应该成为项目长期记忆。关键不是写得多，而是让规则短小、可执行、可验证、不过期。


## 把反复纠正的事实放到 Agent 每次都能看到的位置

不同工具使用 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules/`、`.github/copilot-instructions.md` 等文件，但适合存放的内容相似：

- 构建、测试、格式化和局部测试命令。
- 仓库结构、领域术语和关键架构边界。
- 必须遵守的安全、数据和 Git 约束。
- 指向规范和优秀示例的短链接。

不应长期保存：

- 当前任务进度、临时错误、一次性文件列表。
- 密钥、个人信息和生产数据。
- 整份风格指南或可由 Linter 自动执行的规则。
- 只发生过一次、尚未证明会重复的偏好。

规则越长，越可能互相冲突或被忽略。优先写“何时做什么、如何验证”，并链接到权威文件。

## 订单服务最小规则

```markdown
# 订单服务 Agent 规则

## 命令
- 目标测试：`./mvnw -Dtest=OrderCancellationTest test`
- 相关模块：`./mvnw test`
- 提交前：运行项目静态检查与 `git diff --check`

## 架构
- HTTP 适配在 `web/`，用例编排在 `application/`，业务状态规则在 `domain/`。
- 领域对象不得直接调用支付、消息或数据库客户端。
- 新实现先参考 `CancelShipmentUseCase` 及其测试模式。

## 订单约束
- 状态变更必须通过领域方法并保留审计信息。
- 外部副作用必须有幂等键和可恢复记录。

## 安全与 Git
- 不读取或输出真实支付凭证；不自动执行迁移、提交、推送或部署。
- 保留用户未提交改动，只修改当前任务列出的文件。
```

如果只有 `domain/**` 需要更严格的纯领域规则，可用路径级指令声明“不得依赖 Spring 和基础设施包”；不要让这条规则污染文档或测试资源目录。

## 可以怎样做

1. 收集过去两次以上出现的 Agent 错误或人工纠正。
2. 判断它是可自动检查、长期规则还是一次性上下文。
3. 可自动检查的交给 Linter/测试；长期规则写进项目指令。
4. 为规则提供命令或权威示例，避免抽象口号。
5. 规则进入版本控制，由团队评审。
6. 每次架构或命令变化时同步更新，删除过期规则。

## 动手梳理

把以下内容分类：

- “本次只改 6 个文件”→任务上下文。
- “所有领域状态变化必须经领域方法”→长期规则。
- “代码缩进 4 空格”→格式化工具。
- “生产数据库密码”→任何规则文件都不允许。
- “Agent 第二次忘记运行模块测试”→长期规则或 Hook 候选。

然后为订单服务写 8～12 行项目规则，至少包含命令、架构、安全和 Git 四类。

## 自查清单

- [ ] 规则短小，能在一次阅读中理解。
- [ ] 每条规则长期有效且有触发条件或验证方式。
- [ ] 一次性任务状态和敏感信息没有写入。
- [ ] 路径级规则只影响真正需要的目录。
- [ ] 规则与项目实际命令、目录和示例一致。

## 实战速查卡

### 什么时候查这篇文章

- Agent 反复忘记同一命令或边界。
- 不同会话产生相同错误。
- 仓库级规则与目录级规则混在一起。
- 规则文件越来越长且相互冲突。

### 先做什么

- 收集重复出现的纠正。
- 区分自动检查、长期规则和一次性上下文。
- 把可自动检查的交给工具。
- 为长期规则提供命令或示例。
- 纳入版本控制并定期删旧。

### 可直接借鉴的方法

长期规则优先记录：标准命令、架构边界、领域术语、安全与 Git 约束、权威示例链接。一次性进度、临时错误和敏感数据不要写入。

### 常见误区

- 把任务进度写成长期规则。
- 复制整份风格指南。
- 用抽象口号代替命令。
- 路径级规则污染整个仓库。
- 规则变更后不维护。

### 完成证据

- 8～12 行最小规则。
- 每条有触发条件或验证方式。
- 仓库级与路径级边界。
- 团队评审和版本记录。
