# 从 VibeCoding 到 Agentic Engineering

导航：[[VibeCoding课程首页]] · [[VibeCoding实战问题索引]] · [[VibeCoding课程总纲]] · 下一篇 [[02-Agent Harness原理]]

> [!summary] 核心问题
> AI 几分钟就写出了一个能运行的功能，为什么工程师还不能放心交付？
> 真正的区别不在“要不要使用 AI”，而在“谁控制过程、什么才算完成”。

## 读完你会理解什么

不需要背诵复杂定义，重点是理解：

- 看出“接口调用成功”和“功能可以交付”之间缺少了什么。
- 区分哪些事情由人决定、哪些事情交给 Agent 执行、哪些结果必须由工具证明。
- 为贯穿这一系列文章的“订单取消”功能写出第一版风险边界。
- 写出一句能阻止 Agent 过早修改代码的停止条件。

最终产物是一张“订单取消的人机职责与风险边界表”。后面的 Spec、Plan、测试和评审都会从它继续生长。

## 一、先看一个很真实的下午

下午 4 点，产品经理找到你：

> “订单系统需要增加取消功能。只要订单还没发货，用户就能取消。明天要演示，今天能做完吗？”

你打开 AI 编码工具，输入：

```text
请给 Spring Boot 订单系统实现取消订单功能。
```

不到一分钟，AI 生成了 Controller、Service 和 Repository 代码。你启动项目，调用接口：

```http
POST /api/orders/1001/cancel
```

接口返回 `success: true`，数据库里的订单状态也从 `PAID` 变成了 `CANCELED`。

看到这里，你很可能产生一种自然的感觉：

> “接口能调用，状态也改了，这个功能差不多完成了。”

### 先暂停 30 秒

不要继续往下读。试着回答下面五个问题：

1. 如果订单已经发货，这段代码会拒绝取消吗？
2. `PAID` 订单取消后，支付平台真的退款了吗？
3. 用户连续点击两次，会不会触发两次退款？
4. 两个请求同时取消同一订单，会发生什么？
5. 系统记录了谁在什么时间因为什么原因取消吗？

如果其中任何一个问题答不上来，就不能说功能已经完成。

> [!important]
> **接口返回成功，只能证明某一条路径跑通了。**
> 它不能证明业务规则正确，也不能证明异常、并发、退款和审计都安全。

这里最重要的起点：**能运行，不等于能交付。**

## 二、VibeCoding 到底是什么

VibeCoding 并不是“使用 AI 写代码”的同义词，也不一定是贬义词。它描述的是一种主要凭感觉推进的开发方式：

```text
说出大致想法
→ AI 猜测缺失信息
→ AI 生成大量代码
→ 运行一条成功路径
→ 看起来没问题
→ 继续追加需求
```

如果你只是制作一个随时可以丢弃的页面原型，这种方式可能非常高效。颜色不对就重来，代码坏了也没有真实用户受损。

但订单取消不一样。它可能涉及退款、库存、优惠券、积分、消息通知和审计。一处“看起来合理”的猜测，就可能变成重复退款或账实不一致。

### “能跑”和“可交付”的差别

| 只证明能跑 | 还要证明可交付 |
|---|---|
| 一次请求返回成功 | 所有允许和禁止状态都有明确规则 |
| 数据库状态发生变化 | 本地状态与外部退款保持一致 |
| AI 表示任务已完成 | 测试、日志、Diff 和评审提供证据 |
| 正常路径没有报错 | 重复请求、并发请求、退款失败有处理 |
| 当前演示效果正确 | 变更范围清晰，未来能够维护和追踪 |

判断两者时，可以问自己一句：

> “我现在相信它，是因为我看到了证据，还是因为它刚好没有报错？”

## 三、什么是 Agentic Engineering

Agentic Engineering 不是换一个更强的模型，也不是写一条更长的“万能提示词”。

它是一种工程控制方式：人先说明意图和边界，Agent 在边界内探索与执行，工具持续提供证据，人再根据证据决定继续、修正还是停止。

```text
人定义目标、边界和风险
        ↓
Agent 探索、提出方案并执行小步修改
        ↓
测试、编译、日志和 Diff 产生证据
        ↓
人审查证据，决定继续、修正或停止
```

这个过程没有削弱 AI。它让 AI 承担更多搜索、分析和执行工作，同时避免把业务责任也一起交出去。

### 三方分别负责什么

| 角色 | 核心职责 | 订单取消示例 |
|---|---|---|
| 人 | 决定意图、业务规则、风险接受和最终授权 | 决定 `SHIPPED` 订单是否允许管理员强制取消 |
| Agent | 搜索、分析、提出候选方案、生成测试和执行局部修改 | 查找所有写入订单状态的代码 |
| 工具 | 提供能够复查的客观结果 | 运行测试、显示编译结果、日志和 Git Diff |

工具只能产生结果，不能替人解释全部意义。例如 `BUILD SUCCESS` 证明已有测试通过；但如果没有“重复退款”的测试，它就不能证明幂等性正确。

> [!tip] 一个实用判断法
> - 涉及“应该怎样”的业务取舍，通常由人决定。
> - 涉及“去哪里找、按方案怎么做”，通常可交给 Agent。
> - 涉及“到底有没有通过”，必须查看工具证据。

## 四、同一个需求，两种不同的起点

### 起点 A：直接生成

```text
给订单系统加一个取消功能，写得完整一点。
```

“完整一点”没有说明允许状态、退款失败、一致性、幂等、并发、可修改范围和验证证据。Agent 只能自己补齐空白。

### 起点 B：先探索，再决定

```text
先不要修改代码。

请定位：
1. 订单状态定义与状态流转逻辑；
2. 当前订单操作入口；
3. 支付退款接口；
4. 与订单状态相关的现有测试。

请输出：
- 代码地图；
- 已确认的业务规则；
- 仍然未知的问题；
- 可能受影响的文件；
- 需要人工决定的高风险点。

在我确认前，不要执行数据库迁移、真实退款、Git 提交或代码修改。
```

第二种写法不是拖慢开发，而是在实现前先减少未知信息。对于需要长期维护的代码，先花几分钟避免错误方向，通常比生成后大面积返工更快。

## 五、动手梳理：完成第一张工程化表格

### 先找出“错了会怎样”

先不要想实现方案。请在自己的笔记中写出至少五项风险：

| 风险类别 | 需要回答的问题          |
| ---- | ---------------- |
| 状态   | 哪些不该取消的订单可能被取消？  |
| 退款   | 钱可能被少退、多退或重复退吗？  |
| 幂等   | 同一个请求执行两次会怎样？    |
| 并发   | 两个请求同时操作同一订单会怎样？ |
| 审计   | 出错后能否知道谁做了什么？    |

> [!example]- 完成后再展开参考答案
> - 状态：`SHIPPED` 订单被错误取消。
> - 退款：订单已经标记取消，但支付平台退款失败。
> - 幂等：重复请求触发两次退款。
> - 并发：两个请求都读取到 `PAID`，随后重复执行取消流程。
> - 审计：没有记录操作者、原因、原状态和处理结果。

### 再给责任找到主人

判断下面六项分别属于“人决定”“Agent 执行”还是“工具证明”：

1. `SHIPPED` 订单是否允许管理员强制取消。
2. 查找所有写入订单状态的代码。
3. 判断单元测试是否通过。
4. 选择退款失败时采用同步回滚还是异步补偿。
5. 生成订单取消的候选测试用例。
6. 确认最终 Diff 没有修改无关文件。

> [!example]- 完成后再展开参考判断
> - 人决定：1、4。它们包含业务取舍和风险接受。
> - Agent 执行：2、5。它们是检索和候选内容生成。
> - 工具证明并由人审阅：3、6。必须看到真实测试输出和 Diff。

### 最后写下本阶段的停止条件

停止条件说明：在什么证据出现前，不允许进入下一阶段。

```text
当前阶段只探索，不修改代码。
输出代码地图、已确认规则、未知问题、影响文件和高风险点后停止，
等待人工确认，再决定是否进入 Spec 和实现阶段。
```

合格的停止条件要同时说明：当前允许做什么、禁止做什么、必须交付什么，以及何时停下来等待人。

## 六、把核心观点压缩成一句话

尝试补全：

> VibeCoding 与 Agentic Engineering 的主要差别，不是有没有使用 AI，而是……

一种合格的表达是：

> 前者容易凭生成结果和直觉推进；后者由人控制目标、边界和风险，让 Agent 受控执行，并用工具证据决定是否完成。

只要你的表述包含“人控制边界”“Agent 执行”“证据验证”，就说明抓住了核心。

## 自查清单

- [ ] 我能解释为什么一次接口成功不能代表功能可交付。
- [ ] 我的风险表覆盖状态、退款、幂等、并发和审计五类。
- [ ] 我能区分人决定、Agent 执行和工具证明。
- [ ] 我没有把业务取舍或最终责任交给模型。
- [ ] 我写出了一条“先探索、不改代码、产出后停止”的条件。
- [ ] 我能用自己的话复述 VibeCoding 与 Agentic Engineering 的差别。

如果有任意一项没有完成，回到对应小节补齐即可，不必重新阅读整篇文章。

## 实战速查卡

### 什么时候查这篇文章

- AI 收到一句模糊需求后立刻生成大量代码。
- 功能已经能运行，但你不知道能否交付。
- AI 在替你决定业务规则或风险取舍。
- 任务越做越大，不知道什么时候应该暂停。

### 先做什么

1. 暂停代码修改和高风险操作。
2. 用一句话写清业务目标。
3. 列出“做错会怎样”，优先检查资金、数据、权限和不可逆操作。
4. 把事项分为“人决定、Agent 执行、工具证明”。
5. 写明当前阶段的产物和停止条件。

### 可直接借鉴的探索请求

```text
先不要修改代码。

请定位与当前需求相关的入口、核心规则、外部依赖和现有测试。

请输出：
- 代码地图；
- 已确认事实；
- 未知问题；
- 可能受影响的文件；
- 需要人工决定的高风险点。

输出上述内容后停止，等待我确认。
未经确认，不要修改代码、执行外部副作用、提交或推送 Git。
```

### 常见误区

| 误区 | 修正方法 |
|---|---|
| 一次请求成功就认为完成 | 检查业务边界、异常、重复请求、并发和审计 |
| 让 Agent 自己补全业务规则 | 把未知项显式列出，交给人确认 |
| 用“写完整一点”表达质量要求 | 写出验收条件、验证方式和停止条件 |
| 只看 AI 的完成总结 | 查看测试、编译、日志、Diff 和人工评审 |
| 一开始就授权完整实现 | 先授权只读探索，再逐步扩大权限 |

### 完成证据

- 一张风险边界表。
- 一张人、Agent、工具的职责表。
- 一条包含允许、禁止、产物和等待点的停止条件。
- 一组来自真实工具而非模型自述的验证结果。

## 结语

本文没有让 AI 写任何业务代码，但我们完成了更重要的准备：

1. 看见“能运行”与“可交付”之间的距离。
2. 找到订单取消最先需要控制的五类风险。
3. 明确人、Agent 和工具的职责。
4. 学会用停止条件阻止任务过早进入实现。
