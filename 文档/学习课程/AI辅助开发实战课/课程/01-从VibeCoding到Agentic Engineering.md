## 讲解：不是“少写代码”，而是改变控制方式

VibeCoding 常见路径是：描述一个想法→接受一大段生成代码→看到页面或接口能运行→继续追加提示。它适合低风险原型，却容易跳过真实需求、现有架构、异常路径和验证证据。

Agentic Engineering 的重点不是换一个更强模型，而是建立受控循环：

1. 人定义目标、业务边界、风险、验收和权限。
2. Agent 探索代码、提出方案、编辑文件并运行工具。
3. 测试、编译、日志、Diff 和人工评审提供反馈。
4. 不满足证据就继续修正；达到停止条件才交付。

Agent 可以比人更快地搜索和执行，但不能替你承担业务决策、生产风险或最终签字。尤其在退款、并发和审计等场景中，“模型说完成了”不等于系统行为正确。

## 示例：两个订单取消请求

**低质量请求**

```text
给订单系统加一个取消功能，写得完整一点。
```

它没有说明允许状态、退款失败、一致性、幂等、验收和可修改范围。Agent 只能猜。

**工程化起点**

```text
先不要改代码。请定位订单状态流转、取消入口、支付退款接口和现有测试。
输出：代码地图、已确认规则、未知问题、可能影响文件和高风险点。
未经确认不要执行数据库迁移、外部退款或 Git 提交。
```

第二个请求没有提前给出实现结论，而是先收集决策所需证据，并设置权限边界。

## 操作步骤

1. 写下订单取消的业务目标：用户可以取消尚未发货的订单。
2. 列出“错了会怎样”：重复退款、已发货仍取消、状态与退款不一致、审计缺失。
3. 把职责分为三栏：
   - 人决定：业务规则、风险接受、生产权限和最终合并。
   - Agent 执行：检索、方案草拟、测试生成、局部修改和命令运行。
   - 工具证明：测试结果、静态检查、日志、Diff 和 CI。
4. 为本次学习设停止条件：先得到可信代码地图，不直接生成完整功能。

## 练习

把下面 6 项分别标为“人决定”“Agent 执行”或“工具证明”：

1. `SHIPPED` 订单是否允许管理员强制取消。
2. 查找所有写入订单状态的代码。
3. 判断单元测试是否通过。
4. 选择退款失败时采用同步回滚还是异步补偿。
5. 生成候选测试用例。
6. 确认最终 Diff 没有修改无关文件。

参考判断：1、4 属于人决定；2、5 可由 Agent 执行；3、6 需要工具输出并由人审阅。

## 验收标准

- [ ] 能用一句话解释 VibeCoding 与 Agentic Engineering 的差别。
- [ ] 风险表至少包含状态、退款、幂等、并发和审计五类。
- [ ] 每个高风险决策都有明确责任人，不把最终责任交给模型。
- [ ] 已写出一个“先探索、不改代码”的停止条件。

## 课后小结

高效 AI 开发不是把控制权一次性交给模型，而是把工作拆成可观察、可验证、可停止的循环。下一课将拆解支撑这个循环的 Agent Harness。
