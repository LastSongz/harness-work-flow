# 项目组 AI-SDD 阶段性方案 v0.2

> 文档状态：内部讨论稿
> 适用范围：一个 US 只影响一个代码仓库的场景
> 更新日期：2026-07-15

## 一、执行摘要

本方案的目标不是单纯把 Spec 写进代码仓库，也不是把 Spec 复制到 US 看板，而是建立一条可治理的 AI 研发链路：

> 以经过评审的 Approved Spec 为指令源，驱动内部 AI 编码工具生成高质量代码，并通过计划、测试、自动检查和人工评审形成质量闭环。

SDD 负责把需求转化为结构化、可评审、可追溯的规格；AI 编码工具负责读取 Spec、代码和项目约束并执行；OpenSpec 管理 Change 生命周期；Git MR 保存版本与批准证据。Spec 完整并不等于代码天然高质量，仍需要完整的工程 Harness。

## 二、阶段性流程

```text
业务方提交 RR
  → PO 评审形成 IR
  → BA 拆分候选 US 的业务边界（此时尚未创建正式 US）
  → 项目经理分配单一目标仓库、开发接口人和测试接口人
  → BA 整理当前候选 US 的 IR 输入
  → AI 编码工具 + OpenSpec 生成 Change 草案
  → 创建 Draft Spec MR
  → 业务方线上确认，BA 回写正文并由独立人员见证
  → 开发接口人和测试接口人评审
  → MR Ready，通过保护规则后合入，形成 Approved Change
  → BA 从 Approved Spec 生成正式 US 摘要，附 Spec 链接和 Commit SHA
  → 开发者拆正式 Task，完成正式估算
  → AI 编码工具输出实施计划，通过计划门禁
  → OpenSpec Apply，按 Task 小步生成代码和测试
  → 自动检查、人工评审和 Code MR
  → 发布
  → OpenSpec Archive，更新长期 Spec
```

固定映射关系：

```text
一个 IR → 一个或多个候选 US
一个候选 US → 一个目标代码仓库
一个正式 US → 一个 OpenSpec Change → 一组开发 Task
```

可以把正式 US 看板记录放在 Approved Spec 之后创建，但不能把 US 的业务边界拆分也推迟到 Spec 之后。否则 AI 容易针对整个 IR 生成粒度过大的 Spec，导致后续无法独立评审、估算和交付。

## 三、各系统的事实源边界

| 信息 | 事实源 | 说明 |
|---|---|---|
| RR、IR、业务优先级和原始交付范围 | 需求管理系统 | 保留现有业务治理职责 |
| Spec 使用的 IR 正文、表格和附件版本 | IR 输入快照 | 证明 Spec 基于哪一版原始材料 |
| 已批准、尚待实现的未来系统行为 | Approved OpenSpec Change | 以 Spec MR 的合入提交定位基线 |
| 已实现的当前系统行为 | Archive 后的长期 Spec + 代码 | 只有实现和验证完成后才能 Archive |
| 人员、排期、工时和流程状态 | US / Task 看板 | 仅作为管理视图，不作为详细需求事实源 |

US 看板没有严格的版本控制，也不支持自定义字段。因此 US 中未经 Spec MR 的业务规则、范围或验收标准修改，不应自动成为有效需求变更；冲突时以仓库中的 Approved Spec 为准。

## 四、角色与评审责任

| 角色 | 主要责任 |
|---|---|
| 业务方 | 确认业务目标、规则、范围和验收意图 |
| BA | 拆候选 US、整理 IR 输入、维护业务 Spec、发起 MR、回写确认结论、生成正式 US |
| 项目经理 | 分配目标仓库、开发接口人和测试接口人，检查流程条件 |
| 开发接口人 | 确认仓库和技术可行性，维护设计与任务草案，评审技术内容 |
| 测试接口人 | 评审验收标准、异常边界、测试数据和回归范围 |
| AI 编码工具 | 在授权范围内生成、修改和校验 Spec、计划、代码与测试，不承担批准责任 |

业务方默认没有代码仓库权限。v0.1 的推荐做法是：业务方在线会议确认，BA 将结论回写 Spec 正文，并记录确认人、时间、参与人、对应提交和独立见证人。条件允许且权限边界合适时，可给业务方最小只读和评论权限，让其直接评论 Spec MR，但不应默认开放整个源码仓库。

## 五、IR 输入与附件控制

IR 正文大多数可以复制为文本，但表格和附件通常包含会直接影响开发或验收的正式规则。BA 在调用 AI 前，应针对单个候选 US 整理输入包：

- IR 编号、链接、更新时间和候选 US 临时编号；
- 业务目标、范围、非目标、规则和初步验收标准；
- 表格的结构化结果；
- 附件中的正式规则摘录；
- 每条规则的来源位置及开放问题。

旧附件可能被删除并替换，上传时间无法恢复历史内容。因此原则上需要为 Spec 所用输入建立快照或不可变清单，并记录文件名、上传时间、大小、摘要和存储位置。快照存放在代码仓库、Git LFS 还是内部制品库尚未确认；在方案明确前，首轮试点应优先选择纯文本 IR，或附件已有可恢复版本存储的需求。

## 六、Spec MR 与保护规则

Draft MR 用于澄清，Ready MR 用于批准，Merge Commit 用于形成 Approved Change。建议主分支启用：

- 禁止直接推送，必须经 MR 合入；
- MR 作者不能批准自己的 MR；
- 开发接口人和测试接口人必须独立批准；
- 所有评审线程必须解决；
- 业务确认和 BA 回写证据必须完整；
- Spec MR 不混入正式业务代码；
- 阻塞性开放问题清零后才能进入 Ready。

业务确认采用按影响升级：IR 范围内的细化和规则调整由 BA 与业务方确认；扩大范围、改变核心目标、影响里程碑或其他团队时，再由项目经理判断是否升级 PO。

## 七、Spec 到 US 的同步

US 只保存管理所需的摘要，不复制完整 Spec。由于看板暂不支持自定义字段，v0.1 采用人工同步，在 US 正文顶部固定写入：

```text
OpenSpec Change ID：
Spec MR：
Approved Commit SHA：
Spec 路径：
同步时间：
内容状态：Approved

以下内容由 Approved Spec 生成。业务规则、范围或验收标准如需变更，
必须先通过 Spec MR，不得只修改 US 正文作为开发依据。
```

US 正文只同步用户价值、范围与非目标摘要、主要业务规则、验收标准和依赖关系。BA 完成同步，项目经理或另一名 BA 复核。DevOps 平台是否提供读取、更新 US 正文及查询修改版本的 API 尚不明确；确认具备 API、服务账号和并发控制后，再设计自动同步与一致性告警。

## 八、AI 编码工具、OpenSpec 与 Jenkins

当前指定的 AI 工具是基于开源 OpenCode 二次开发的内部 AI 编码工具，接入内部部署的大模型。已知 AI 编码工具可以读取代码仓库；IR 暂无技术接入方式，但不存在安全合规阻碍，因此 v0.1 由 BA 人工整理 IR 输入。

不能因为 AI 编码工具基于 OpenCode，就假设它与 OpenSpec 完全兼容。试点前需要 PoC 验证：

- 是否读取仓库中的项目和 OpenSpec 指令；
- 是否可以创建、修改 `openspec/changes/`；
- 是否可以执行 `openspec validate` 等 CLI 命令；
- 是否支持中文 Spec、跨会话继续 Change；
- 是否能限制只修改 Spec，避免评审前提前修改业务代码。

现有流水线由基于 Jenkins 建设。能否安装固定版本的 OpenSpec、执行 validate 并把结果设为 MR 必过状态仍待探索。v0.1 可先由 BA 或开发接口人本地校验并在 MR 中记录工具版本、执行人、时间和结果；验证 Jenkins 能力后再升级为自动门禁。

## 九、高质量代码的五道门禁

SDD 只提高 AI 输入质量，不能独自保证代码质量。完整闭环至少需要：

1. **Spec 门禁**：范围、规则、异常、权限、边界、验收标准和技术影响明确，阻塞问题归零。
2. **计划门禁**：AI 编码工具写代码前先输出文件影响、任务顺序、测试方案、数据与接口变化、发布和回滚风险，由开发接口人批准。
3. **小步实现门禁**：一次只处理一个 Task，先补测试，再做最小代码修改，验证 Diff 后才进入下一项。
4. **自动化门禁**：执行构建、单元测试、集成测试、静态检查、格式检查及必要的安全扫描，以命令结果而非 AI 自述作为证据。
5. **人工评审门禁**：开发检查设计与可维护性，测试检查场景和回归，BA 检查业务行为，项目经理检查范围和交付是否失控。

建议形成以下追溯链：

```text
业务规则 BR → 验收标准 AC → 测试用例 TEST → 实施 Task → Code Commit
```

Code MR 至少记录使用的 Spec Commit、实现的 Task、覆盖的 AC、测试证据和未自动验证项。

## 十、试点衡量指标

- AI 代码首次构建通过率；
- 自动测试首次通过率；
- Code Review 问题数量及类型；
- 因需求理解错误产生的返工次数；
- AI 修改范围外文件的次数；
- 测试和验收阶段发现的缺陷数；
- 人工修改 AI 代码的比例；
- 从 Spec Approved 到 Code MR 的耗时。

首轮指标用于验证流程与改进 Harness，不用于个人绩效评价。

## 十一、已确认事实与开放问题

### 已确认事实

- 一个 IR 经常拆成多个 US；一个 US 不影响多个代码仓库。
- 项目经理能在正式 US 创建前分配目标仓库、开发接口人和测试接口人。
- BA 具备代码仓库、Git、MR 和 OpenSpec 的基本操作条件。
- 代码仓库支持保护主分支、必选评审人或最低批准人数。
- 业务方可在线确认；必要时也可开通最小仓库评论权限。
- AI 编码工具使用内部部署模型，代码仓库可读，IR 的障碍是技术接入而不是合规。

### 开放问题

1. IR 附件快照是否允许保存到代码仓库或 Git LFS；如不允许，使用哪个内部版本化存储？
2. 内部 DevOps 平台 是否提供 US 正文读写、修改历史、Webhook、服务账号和并发控制 API？
3. AI 编码工具是否能完整兼容 OpenSpec 工作流并执行 CLI？
4. Jenkins 是否能运行固定版本的 OpenSpec validate，并作为 MR 必过检查？
5. Spec 与代码模板需要如何适配项目组现有 Java 技术栈和质量规则？
6. **用于首轮试点的代码仓库，是否已经具备稳定的构建、单元测试、静态检查和 MR 流水线？**

第 6 项是下一轮讨论的起点。若试点仓库缺少稳定的自动化基础，试点只能证明 AI 可以生成代码，不能证明 AI 可以稳定生成高质量代码。
