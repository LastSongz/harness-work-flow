# 华为海思供应链 SDD 初步探索报告 v0.1

> 文档状态：内部讨论稿
> 适用范围：华为海思供应链项目组单 US、单代码仓库场景
> 更新日期：2026-07-14

## 执行摘要

本报告探索在现有 RR、IR、US 需求链路之后，引入仓库内 Spec 的可行方式。目的不是替换华为既有流程，而是将开发前后的需求澄清、系统行为、技术约束和验收标准沉淀为可评审、可追溯的开发基线。

初步建议的主流程为：业务方下发 RR，PO 评审形成 IR，BA 将 IR 拆解为 US；开发者接收 US 后创建 Draft Spec MR，围绕 Spec 完成反串讲及 BA、开发、测试评审，合入形成 Approved 基线，再拆解 Task 并给出正式估算。

首版采用“一个 US 对应一个 Spec”的轻量模式。上游需求系统继续管理业务来源、范围与优先级，代码仓库中的 Approved Spec 管理系统行为、技术契约和验收标准，两类事实源通过 RR、IR、US 编号建立追溯。

## 一、现状流程与主要痛点

### 1.1 现状流程

当前工作流程大致为：业务方下发 RR，经华为方 PO 评审后形成 IR；IR 进入 BA，由 BA 分析并拆解为 US；开发者接收 US 后自行拆解 Task，评估工作量和预计完成时间，再进入开发。

开发前通常还会进行需求分析和反串讲，业务方、BA、开发及相关人员共同澄清需求。这个过程能够解决大量问题，但澄清结论的沉淀位置并不总是统一。

### 1.2 主要痛点

开发中发现的新问题往往需要二次澄清。结论可能留在聊天记录、会议纪要、需求看板或个人笔记中，后续参与者难以快速判断哪一版结论有效，也难以追溯某段代码所依据的业务规则。

开发者在仅拿到 US 时就拆 Task 和承诺工期，可能仍有业务边界、异常场景或技术影响没有暴露。此时给出的精确估算容易失真，后续澄清也可能带来返工和排期调整。

## 二、SDD 初步方案

SDD 在本方案中指 Spec-Driven Development。核心做法是在 US 与正式开发之间建立仓库内 Spec，用版本控制和 MR 评审收敛需求分析结果，再以已批准 Spec 作为系统行为与实现验收的基线。

建议主流程如下：

```text
业务方下发 RR
  → PO 评审并形成 IR
  → BA 分析 IR、拆解 US
  → 开发者创建 Draft Spec MR
  → 围绕 Spec 进行需求反串讲
  → BA、开发、测试评审并回写结论
  → Spec MR 合入，形成 Approved 基线
  → 开发者拆解 Task，完成正式估算
```

v0.1 建议采用以下映射：一个 IR 可以拆为一个或多个 US；一个 US 对应一个 Spec 目录；一个 Spec 对应一组实施 Task。首轮只验证单 US、单仓库场景，暂不处理跨仓库规格编排。

Spec 不复制 RR、IR、US 的全部内容，而是引用上游编号和链接，补充实现与验收所必需的精确业务规则、边界场景、技术设计、测试策略和重要决策。

## 三、RR、IR、US、Spec、Task 的事实源边界

| 产物 | 主要责任方 | 主要回答的问题 | 建议事实源 |
|---|---|---|---|
| RR | 业务方 | 原始业务诉求是什么 | 华为需求系统 |
| IR | PO、BA | 哪些诉求进入交付 | 华为需求系统 |
| US | BA | 本次交付什么用户能力 | 华为需求系统或看板 |
| Spec | Spec Owner、BA、开发、测试 | 系统应如何表现、如何实现和验收 | 代码仓库 |
| Task | 开发者 | 如何实施已批准 Spec | 华为研发任务系统 |

华为需求系统是业务来源、交付范围和优先级的事实源；代码仓库中的 Approved Spec 是系统行为、技术契约和验收标准的事实源。两者各有边界，不应相互替代。

聊天、会议纪要和 MR 评论仍可用于讨论，但其中产生的有效结论应回写 Spec 正文。未回写的口头结论或聊天记录不宜直接作为开发依据。

仓库内 `tasks.md` 只记录实施逻辑、依赖、完成条件、验证方式和外部 Task 链接。Task 的负责人、状态和工时仍以现有研发任务系统为准，避免两套状态并行维护。

## 四、Spec MR 生命周期

### 4.1 Draft：用于澄清

开发者接收 US 并完成初步分析后，即可创建 Draft Spec MR，不必等待所有问题解决。Draft 至少应包含上游需求链接、目标、初步范围、非目标、主要流程、核心规则、初步验收标准及开放问题。

需求反串讲围绕 Draft Spec 展开。业务规则写入需求规格，技术结论写入设计说明，重要取舍写入决策记录。会议结束后由 Spec Owner 收敛修改，避免结论只停留在会议纪要中。

### 4.2 Ready：用于批准

当目标、范围、术语、业务规则、正常与异常场景、权限与边界、验收标准以及主要技术影响均已明确，阻塞性开放问题归零，且各文档内容一致时，Draft MR 才进入 Ready 状态。

Ready 表示该 Spec 已具备正式评审和批准条件，并不代表已经生效。评审意见仍需落实到正文，不能仅以评论中的口头确认代替文档修改。

### 4.3 Merge：形成基线

BA 或业务责任人确认需求内容，开发负责人确认技术可行性和影响范围，测试负责人确认验收标准及场景可测试。评审线程关闭并完成必要批准后，Spec MR 方可合入主分支。

合入后形成 Approved Spec 基线，可由“Spec 目录 + 主分支 + Merge Commit SHA”唯一定位。后续开发及代码 MR 应引用该基线；影响系统行为或验收标准的变更，应先更新 Spec 并完成评审。

## 五、角色责任

| 角色 | 初步责任 |
|---|---|
| 业务方、PO | 维护 RR、IR 的业务方向、范围和优先级 |
| BA | 拆解 US，确认 Spec 不偏离 IR、US 和业务规则 |
| Spec Owner | 默认由承接 US 的开发者担任，创建 Draft MR、补充工程信息、收敛评审意见 |
| 开发负责人 | 评审技术方案、接口、数据、兼容性、风险及影响范围 |
| 测试负责人 | 评审验收标准、正常与异常场景、回归范围和可测试性 |

角色分工的重点不是增加审批层级，而是让业务正确性、技术可行性和可测试性分别有人负责。具体批准人和替代机制仍需结合项目组现有组织方式讨论。

## 六、工作量估算分为两个阶段

开发者接收 US 后可以给出区间式初步估算，用于容量和排期判断。此时应明确估算依据与主要未知项，不宜作为最终承诺，例如使用“3～5 人日”而不是过早给出单一精确数字。

Spec Approved 且 Task 拆解完成后，再基于稳定的范围、技术影响和验收要求给出正式工作量及预计完成时间。如果后续发生影响范围或系统行为的变更，应同步重新评估。

## 七、预期收益

- 建立统一的需求澄清载体，减少结论散落在聊天、会议和个人笔记中的情况。
- 通过 Git 与 MR 保留规则变化、评审过程和决策依据，增强需求到代码的追溯能力。
- 在正式拆 Task 前暴露业务边界和技术风险，提高估算质量，减少开发中途返工。
- 让 BA、开发和测试围绕同一份 Spec 协作，使业务规则、技术方案和验收标准更早对齐。
- 为后续引入 AI 辅助分析、任务拆解、代码生成和一致性检查提供结构化输入。

这些收益仍属于待验证假设。是否真正改善交付质量与效率，需要通过真实需求试点和数据复盘判断。

## 八、风险与控制建议

### 8.1 文档负担增加

如果 Spec 追求一次性完整，可能增加前期负担并拖慢交付。建议采用“最小可执行 Spec”，先明确足以开工的内容，再在发现新问题时持续演进。

### 8.2 Spec 与上游需求不一致

Spec 不能绕过 RR、IR、US 的审批，也不能擅自扩大交付范围。每个 Spec 应保留上游编号和链接，由 BA 负责确认业务追溯关系。

### 8.3 Spec 与代码逐渐偏离

代码 MR 应引用 Approved Spec 基线，并检查关键验收标准是否有验证证据。影响行为或契约的变更先改 Spec；单纯实现缺陷只修改代码和测试。

### 8.4 评审周期变长

Draft MR 应尽早建立，反串讲和评审尽量围绕同一载体并行推进。v0.1 先采用一个 Spec MR，不拆成多级 MR，以控制流程复杂度。

### 8.5 重复维护 Task 状态

任务负责人、工时和状态继续以现有研发任务系统为准。仓库只保留实施逻辑及链接，不另建完整任务看板。

## 九、首轮试点建议

选择一个边界较清晰、参与方较少、预计 3～10 个开发日、仅涉及一个代码仓库的真实 US。避免首轮选择紧急线上问题、跨系统大改造或仍存在大量业务争议的需求。

试点按完整链路执行：创建 Draft Spec MR、完成反串讲和三方评审、合入 Approved 基线、拆 Task 和正式估算，再进入开发。交付后用一次短复盘判断哪些步骤有价值、哪些模板需要删减。

建议记录：Draft 到 Approved 的时间、开放问题数量、开发中新增澄清次数、Spec 变更次数、估算偏差、需求遗漏和返工情况。首轮数据用于比较和改进，不用于个人绩效评价。

## 十、待项目组讨论的问题

1. BA、开发负责人、测试负责人分别由哪些具体角色承担，批准是否可以授权代理？
2. Draft Spec 应在正式反串讲前创建，还是在开发者完成首次分析后创建？
3. 当前平台如何表达 Draft、Ready、Approved 状态，以及如何配置必要评审人？
4. 首版 Spec 的最小必填项有哪些，哪些内容可以按需求复杂度裁剪？
5. 需求系统、代码仓库和研发任务系统之间如何稳定关联 RR、IR、US、Spec 与 Task？
6. 紧急缺陷、纯技术改造和小范围配置变更是否需要单独的简化流程？
7. 首轮试点选择哪个 US，由谁担任 Spec Owner，复盘周期和成功标准如何确定？

## 初步结论

当前建议是在华为既有 RR、IR、US 流程之后增加仓库内 Spec，而不是重建一套需求管理体系。以 Draft MR 收敛澄清，以 Ready MR 完成批准，以 Merge Commit 建立 Approved 基线，再拆 Task 并进行正式估算。

本报告仅作为项目组内部讨论的 v0.1 草案。后续应通过一个真实 US 试点验证流程成本、协作效果和可执行性，再决定是否形成正式规范及是否引入自动化 Harness。
