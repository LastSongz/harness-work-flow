# Harness / SDD 工作流 v0.1 设计说明

## 1. 背景

现有流程通常经历原始需求、需求分析、反串讲和开发。开发中产生的二次澄清可能散落在聊天记录、会议纪要或需求看板中，后续人员难以判断哪一份信息才是最终结论，也无法稳定地把这些结论提供给 AI 编码工具。

本设计将仓库内经过评审的 Spec 作为“已批准需求与设计决策”的唯一事实源，使业务、开发、测试和 AI 使用同一份上下文。

## 2. 目标

- 让每个需求在开发前具备一份足以开工的最小 Spec；
- 让开发中新产生的业务澄清和技术决策回到仓库；
- 让需求变化可以通过 Git Diff 和 PR 被识别、评审和追溯；
- 让 AI 基于已批准的规格增量修改代码和测试；
- 以较低流程成本完成一个真实需求试点。

## 3. 非目标

- 不要求开发前穷尽所有实现细节；
- 不把聊天、看板或原始业务文档整体复制进仓库；
- 不把 Spec 当成模板去全量重建存量系统；
- v0.1 不解决多仓库编排和平台插件集成。

## 4. 核心原则

### 4.1 渐进式 Spec

开发前形成“足以开工”的最小 Spec，开发中持续完善。Spec 不是一次性文档，也不是开发结束后的补录材料。

### 4.2 先批准行为，再实现行为

凡是改变业务行为、验收标准或外部契约的内容，先更新并批准 Spec，再修改代码。单纯的编码错误不反向修改 Spec。

### 4.3 同库与可追溯

一个业务需求对应一个代码仓库。Spec 与实现代码同库保存，Code PR 必须引用 Spec 路径和作为开发基线的提交。

### 4.4 增量开发

Harness 向 AI 提供已批准 Spec、Spec Diff、当前代码和项目约束。AI 生成差异分析、任务与增量补丁，不覆盖未授权区域。

### 4.5 评审责任不混淆

- 业务负责人确认业务目标、规则、范围和验收标准；
- 开发负责人确认技术方案、接口、影响范围和风险；
- 测试负责人确认场景覆盖、可测试性和回归范围；
- Code Reviewer 确认实现质量以及代码与 Spec 的一致性。

## 5. 资产模型

每个需求使用一个独立目录：

```text
specs/<需求编号>-<简短名称>/
├── requirements.md
├── design.md
├── tasks.md
└── decisions.md
```

- `requirements.md`：目标、非目标、业务规则、场景和验收标准；
- `design.md`：现状、方案、接口、数据、异常、兼容性和测试策略；
- `tasks.md`：按依赖排序的实施任务及验证方式；
- `decisions.md`：开发期间产生的澄清、决定、参与人及其影响。

Spike 仅用于限时技术探索。Spike 的结论如果影响正式实现，必须转写到 `design.md` 或 `decisions.md`，Spike 本身不作为最终需求事实源。

## 6. 状态与门禁

Spec 状态采用：

```text
Draft → In Review → Approved → Implementing → Delivered
                              ↘ Superseded
```

### Spec Gate

进入开发前必须满足：

- 目标、非目标和术语明确；
- 当前开发路径不存在未解决的业务问题；
- 正常、异常和边界场景具备可验证的验收标准；
- 业务、开发、测试完成各自评审；
- Spec PR 已合入目标分支。

### Implementation Gate

Code PR 合入前必须满足：

- 引用 Spec 路径和基线提交；
- 每条验收标准都有测试或人工验证证据；
- 开发期间形成的有效结论已经回写；
- 当前代码行为与已批准 Spec 一致；
- 没有为了迁就偶然实现而反向修改业务要求。

## 7. 开发中问题的分级

| 等级 | 情况 | Spec 动作 | 评审人 |
|---|---|---|---|
| L0 | 原 Spec 明确，代码实现错误 | 不修改 Spec | 开发、测试 |
| L1 | 技术细节调整，不改变外部行为 | 更新 `design.md` 或 `decisions.md` | 开发负责人 |
| L2 | 业务规则、范围、验收标准或外部契约变化 | 先更新 `requirements.md`，批准后再开发 | 业务、开发、测试 |

无法立即判断等级时，按 L2 处理，先停止受影响任务，不阻塞无关任务。

## 8. Harness 在 v0.1 中的职责

v0.1 先用流程约定和模板实现逻辑 Harness：

1. **上下文装载**：读取项目规范、已批准 Spec、Spec Diff 和相关代码；
2. **门禁检查**：未达到 Spec Gate 时不进入正式实现；
3. **变更分类**：把开发中新问题分为 L0、L1、L2；
4. **任务执行**：依据 `tasks.md` 小步修改并逐项验证；
5. **一致性验证**：检查验收标准、测试和 Code PR 的追溯关系；
6. **审计留痕**：通过 Git 提交和 PR 保存规格、决定与实现历史。

待试点验证后，再判断哪些环节值得通过 CI、机器人或 AI Agent 自动化。

## 9. 试点与成功指标

首轮选择一个 3～10 个开发日、单仓库、业务边界清晰的需求。记录：

- Spec 首次评审耗时；
- 开发中 L1、L2 变更次数；
- 聊天结论未回写次数；
- Code PR 因需求理解造成的返工次数；
- 验收阶段发现的需求遗漏数量；
- 团队对流程成本和清晰度的主观评分。

v0.1 的成功标准不是“AI 生成了多少代码”，而是需求事实是否集中、变更是否可追溯、返工是否减少。

## 10. 后续演进

试点通过后再评估：

- 针对实际托管平台的 PR 模板和合并门禁；
- Spec 格式校验、链接校验和验收标准覆盖检查；
- AI 自动生成 Spec Diff 摘要、任务和测试建议；
- 紧急修复的轻量审批与事后回填机制；
- 多仓库需求的主 Spec 与服务级 Spec 关系。
