# 单需求单仓库 SDD 工作流 v0.1

## 1. 总览

```text
原始需求
  ↓
需求分析与反串讲
  ↓
最小 Spec（Draft）
  ↓
Spec PR：业务 + 开发 + 测试评审
  ↓
Spec Approved
  ↓
生成任务并增量开发
  ↓
开发中问题分级：L0 / L1 / L2
  ↓
Code PR：实现、测试与 Spec 一致性评审
  ↓
交付与复盘
```

## 2. 阶段一：需求发现

输入可以是需求看板、原始业务文档、会议记录或口头描述。此阶段允许信息分散，目标是完成分析，而不是立刻追求正式文档。

需求分析人员负责：

- 明确要解决的问题和用户价值；
- 识别业务术语、规则、角色和权限；
- 整理正常、异常和边界场景；
- 标记已知事实、假设和待确认问题；
- 组织业务、开发和测试进行反串讲。

反串讲结论必须进入 Spec Draft，会议记录本身不作为开发依据。

## 3. 阶段二：最小 Spec

从模板创建：

```text
specs/<需求编号>-<简短名称>/
```

开发前不要求穷尽所有技术细节，但必须满足：

- 目标和非目标清楚；
- 当前实施路径没有未解决的业务问题；
- 业务规则不存在互相矛盾；
- 验收标准可观察、可测试；
- 失败、权限和边界行为有明确预期。

未影响当前实施路径的问题可以保留，但必须写明负责人和最晚决策时间。

## 4. 阶段三：Spec PR

Spec PR 只评审“做什么、为什么做、如何验收以及准备如何实现”，不混入正式业务代码。

建议审批责任：

| 内容 | 主要负责人 |
|---|---|
| 目标、范围、业务规则 | 业务负责人 |
| 方案、接口、数据、兼容性 | 开发负责人 |
| 场景、验收标准、回归范围 | 测试负责人 |

所有必须问题关闭后，将状态改为 `Approved` 并合入。该合入提交是后续开发的 Spec 基线。

## 5. 阶段四：计划与开发

AI 或开发人员读取：

- 项目编码与安全规范；
- 已批准 Spec；
- Spec 基线之后的差异；
- 当前代码和测试；
- `tasks.md` 中尚未完成的任务。

每次只执行边界清晰的小任务，并在任务结束时运行对应验证。AI 不应因为 Spec 变化而重建整个模块，也不应修改任务范围之外的代码。

## 6. 开发中问题处理

### L0：实现错误

条件：Spec 已经清楚说明预期行为，代码与其不一致。

动作：修改代码和测试；不修改 Spec。

### L1：技术发现

条件：需要调整内部方案，但业务行为、外部契约和验收标准不变。

动作：更新 `design.md` 或追加 `decisions.md`，由开发负责人评审后继续。

### L2：需求变化

条件：业务规则、范围、外部契约或验收标准发生变化。

动作：

1. 暂停受影响任务；
2. 更新 `requirements.md`，同步更新设计、任务和测试影响；
3. 提交 Spec 变更 PR；
4. 业务、开发、测试重新评审受影响内容；
5. 合入后，基于 Spec Diff 继续增量开发。

任何聊天或会议中形成的 L1、L2 结论，都必须在继续相关开发前回写仓库。

## 7. 阶段五：Code PR

Code PR 至少包含：

- Spec 目录；
- 开发使用的 Spec 基线提交；
- 本次实现覆盖的任务和验收标准；
- 自动测试结果；
- 无法自动化时的人工验证证据；
- 开发期间发生的 Spec 变更链接。

Reviewer 同时评审代码质量和一致性。代码正确但不符合 Spec，或者 Spec 已过期但未更新，都不能合入。

## 8. 阶段六：交付与复盘

交付后将 Spec 状态更新为 `Delivered`，确认任务状态和实际交付一致。复盘重点是：

- 哪些问题在开发前本可发现；
- 哪些澄清仍然散落在仓库之外；
- 哪些模板字段没有产生价值；
- 哪些人工检查值得自动化；
- 流程是否降低了返工，而不是只增加文档工作。
